# SA午後II(科目B-2)論文 事例ストック

## この資料の使い方

手持ちの経歴(製造業の社内SE、在庫・品質担当、.NET Framework 4.8 WinForms+Oracleの2層構成、チームリーダ)から、使い回せる事例を4本用意しました。本番では問題を読んだ瞬間に「どの事例で書くか」を決め、設問に合わせて切り口だけ変えるのが狙いです。

- 各事例は「論述対象の概要(質問書)」「業務背景と課題」「検討した複数案と採用理由」「工夫・評価」「使える設問」の順にまとめています。
- 人数・工数・期間・台数は仮の値です。実際の社内状況に近い数字に置き換えてから練習してください(数字は本番中に考えると時間を食います)。
- 事例C・Dは構想段階の取り組みを「完了した開発」として書く想定です。細部を盛るより、検討の経緯と判断理由の一貫性を優先してください。

採点講評が毎年のように指摘していること(2015〜2025年度の講評より):

1. 問題文の観点を抜き出して一般論とつなげただけの論述は評価されない。
2. 「何をしたか」だけでなく「なぜそうしたか・何と比較したか」が必要。→ 各事例に必ず複数案の比較を入れてあります。
3. 業務特性・業務目的を理解しているかが見られる。「システムの制約」や「プロジェクトの制約」を業務特性と書かない。
4. 運用回避やハード増強だけの解決策は「設計の工夫」と見なされない(2024年度問2)。

## 「論述の対象とする計画策定又はシステム開発の概要」の書き方

この欄は「どんなシステムで、あなたがどの立場で関わったか」を採点者に渡すためのもので、論文本文(特に設問ア)と矛盾しないことが最優先です。問題冊子の記入方法によると、①は名称、②〜⑬は選択肢に○(複数可、必要なら括弧内に追記)、⑭・⑮は括弧内に記入です。複数システムが対象なら主たるシステムについて書きます。

選択肢の正式な文言は問題冊子ではなく答案用紙側にあるため、下の項目名は一般的な構成です。科目B-2はCBTになるため、入力画面の形式はIPAのサンプルや『合格論文の書き方・事例集』の記入例で一度確認しておいてください。

| 項目 | 4事例共通の記入方針 |
| --- | --- |
| 計画又はシステムの名称 | 「〇〇システムの再構築」のように、業務名が分かる名称にする(社内の略称は使わない) |
| 業種 | 製造業 |
| 企業の規模(従業員数) | 実際の勤務先の区分に合わせる(要確認) |
| 対象業務の領域 | 事例ごとに「生産」「物流」「品質管理」など |
| システムの形態・規模 | クライアントサーバ、サーバ台数・クライアント台数を括弧内に |
| ネットワークの範囲 | 「同一企業の複数事業所間」か「単一事業所内」 |
| 利用者数 | 事例ごとに実態に合わせる |
| 総工数・開発期間 | 事例ごとの仮値を実態に合わせる |
| あなたの所属 | 情報システム部門 |
| あなたの担当工程 | 要件定義・基本設計を必ず含める(SAの役割が読み取れるように) |
| あなたの役割・責任範囲 | 「システムアーキテクトとして要件定義と方式設計を担当し、開発チーム(3名)を取りまとめた」を基本形にする |

注意点は2つです。立場を「PM」「プログラマ」だけにするとSAの論文としての前提が崩れます。また、総工数は「人数×期間」と矛盾しない値にしてください(3名×8か月なら約24人月)。

## 事例A 在庫ロケーション管理システムの再構築

最も汎用性が高い「本命」の事例です。普段の業務(在庫、WinForms+Oracle、悲観ロック)に最も近く、要件分析・UI・移行・テストのどの設問にも切り替えられます。

### 論述対象の概要(仮値)

| 項目 | 内容 |
| --- | --- |
| 名称 | 部品・製品倉庫の在庫ロケーション管理システムの再構築 |
| 対象業務 | 物流(入庫・格納・出庫引当・ピッキング・棚卸) |
| 形態 | クライアントサーバ(DBサーバ1台、APサーバ1台、PC約30台、ハンディ端末約10台) |
| ネットワーク | 同一企業の単一事業所内(工場・倉庫) |
| 利用者数 | 約60名(倉庫作業者、生産管理、購買) |
| 工数・期間 | 約30人月・10か月 |
| 立場 | 情報システム部門のSAとして要件定義・基本設計を担当、開発チーム3名を取りまとめた |

### 業務背景と課題

- 在庫数は生産管理システム(Oracle)で品番単位に管理しているが、「どの棚にあるか」は担当者ごとのExcel台帳で管理していた。
- 結果として、部品の探し回り時間、棚卸差異、先入れ先出し違反(古いロットの残留)が発生していた。
- 業務目標：ピッキング時の探し時間を半減し、ロット違いによる誤出庫をゼロにする。

### 検討した複数案と採用理由

| 論点 | 候補 | 採用 | 理由(業務特性に結びつける) |
| --- | --- | --- | --- |
| 実現方式 | (a) WMSパッケージ導入 (b) 既存の生産管理システムに機能追加 (c) Excel台帳の運用改善 | (b) | 在庫数とロケーションの二重管理をなくすことが目的。(a)は生産管理との連携開発と「仮置き」など自社特有の運用とのギャップが大きい。(c)は入力漏れを防げない |
| 現場の入力方式 | (a) ハンディからWeb画面で即時更新(APサーバ追加の3層) (b) ハンディに記録して定時にCSV取込 (c) 事務所PCで後入力 | (a) | 出庫引当はリアルタイムの棚情報を前提とする。(b)(c)では数十分のタイムラグで引当先の棚が空になる事象が残る |
| 同時更新制御 | (a) 悲観ロック (b) 楽観ロック | 棚単位で(a) | 同一棚への同時スキャンは繁忙時に発生する。ロック範囲を品番でなく棚に絞り、待ちを最小化 |

### 工夫(設問ウで使うネタ)

- 移行：Excel台帳ごとに棚番の表記が異なっていた(「A-1-3」と「A01-03」など)。変換表で正規化し、年度末の実棚卸(入出庫を止める日)と同時に初期ロケーションを登録した。「稼働を止められるのは棚卸日だけ」という業務特性が移行タイミングの根拠。
- UI：倉庫作業者は手袋・片手作業のため、キー入力をなくし「棚→品番→ロット」の3回スキャンで完了させた。古いロットを飛ばした場合は音とバイブで警告する。
- テスト：「入荷→格納→引当→ピッキング→出荷→棚卸」の業務サイクルで区分し、朝の出荷ピークを再現した同時スキャン試験を倉庫担当者と実施した。
- 要求の優先順位：要望20件を「誤出庫削減への寄与」「探し時間削減」「実現コスト」で重み付けし、ラベル再発行などは次期に回した。

### 使える設問

2025問2(データ移行)、2021問2・2015問2(機能追加)、2019問1(UI)、2019問2(適格性確認テスト)、2016問1(優先順位)、2016問2(移行方法)。2018問2(パッケージ)は実現方式を(a)に置き換えて書く。

## 事例B 品質指標提供システムの構築

「複数システムのデータを集めて指標を出す」系と「バッチ・非機能・柔軟性」系を担う事例です。品質担当としての業務知識と、組込み出身(検査装置のデータに強い)という強みが生きます。

### 論述対象の概要(仮値)

| 項目 | 内容 |
| --- | --- |
| 名称 | 工程内不良率・市場不良率を提供する品質指標システムの構築 |
| 対象業務 | 生産(品質管理・品質保証) |
| 形態 | クライアントサーバ(DBサーバ1台、PC約20台) |
| ネットワーク | 同一企業の複数事業所間(本社品質保証部と工場) |
| 利用者数 | 約40名(品質保証、製造、設計) |
| 工数・期間 | 約20人月・8か月 |
| 立場 | SAとして指標の定義合意、データ分析、方式設計を担当 |

### 業務背景と指標

- 業務目標：品質保証部が月次品質会議で不良の多い製品・工程を特定し、設計・製造部門の是正処置を早める。
- 現状：担当者が3つのデータをExcelで手集計し、毎月2日かかっていた。会議の時点で既に半月前の数字になっていた。
- 指標：工程内不良率(不良数÷投入数、製品×工程別)と市場不良率(クレーム件数÷出荷数、製造月別、ppm)。
- データの収集元：生産管理システム(投入数・出荷実績・ロット)、検査システム(検査装置の合否・測定値)、クレーム管理台帳(品番・製造ロット・不具合内容)。

### 検討した複数案と採用理由

| 論点 | 候補 | 採用 | 理由 |
| --- | --- | --- | --- |
| 集計方式 | (a) 各システムを画面表示のたびに直接参照 (b) 夜間バッチで集計用テーブル(データマート)を作成 (c) BIツールを導入 | (b) | 検査システムは稼働中のラインと同じDBで、日中に重い集計をかけられない。指標は週次・月次の判断に使うため日次更新で足りる。(c)は品証が会議資料をExcelで加工する運用を変えられず、ライセンス費に見合う効果が説明できない |
| 品番体系の差 | (a) 各システムのコードを統一改修 (b) 品番対応マスタで吸収 | (b) | 検査システムは機種コード、クレームは顧客品番を使う。外部購入の検査ソフトは改修できない |
| 不良の定義 | (a) 一次不良だけ (b) 再検査後の最終不良だけ (c) 両方 | (c) | 製造は手直し工数を見るため一次不良率、品証は流出リスクを見るため最終不良率が必要。部門ごとの意思決定の違いを両方に聞いて確認した |

### 工夫(設問ウで使うネタ)

- データ欠落：クレームの約3割で製造ロットが未記入だった。製品シリアルから出荷実績を逆引きしてロットを補完し、それでも不明なものは出荷月で「みなし」、画面上で推定値と区別して表示した。さらに受付画面でロットを必須にして発生源を断った。
- バッチ：工場は夜勤があり、バッチ中も検査データが書き込まれる。「ロット完了」を確定の単位にし、未完了ロットは翌日に再計算する設計にした。途中で失敗してもそのまま再実行できるよう、処理ごとに削除→再作成で冪等にした。
- 遡及修正：原因調査でクレームの帰責が変わることがあるため、速報値と月次確定値を2本立てにした。
- 柔軟性：指標の分子・分母・集計軸をマスタ化し、新指標はマスタ登録だけで追加できる。ただしコストを抑えるため集計軸は「製品・工程・期間」の3つに絞った。
- 非機能要件の説明：品証部長に「速報性と正確性」のトレードオフを、実際の過去3か月分の試算結果で示して日次更新に合意を得た。

### 使える設問

2025問1(複数システムの指標)、2018問1(データ活用)、2024問2(バッチ設計)、2017問1(非機能要件)、2017問2(柔軟性)。

## 事例C 倉庫デジタルツインによる在庫配置の最適化

DX・PoC・アジャイル系の事例です。事例Aで蓄積したロケーションと入出庫履歴を使う「第2弾」という位置付けにすると、背景説明が簡単になります。実際に作っている3Dマップ・ヒートマップの構想を素材にしています。

### 論述対象の概要(仮値)

| 項目 | 内容 |
| --- | --- |
| 名称 | 倉庫在庫の3次元可視化(デジタルツイン)による在庫配置最適化システムの開発 |
| 対象業務 | 物流(在庫配置計画・ピッキング) |
| 形態 | クライアントサーバ(DBサーバ1台、PC約10台、倉庫内の大型モニタ2台) |
| 利用者数 | 約25名(倉庫班長・作業者、生産管理) |
| 工数・期間 | 約12人月・6か月(PoC 2か月を含む) |
| 立場 | SAとして仮説設定・PoC計画・方式設計を担当 |

### 業務背景とDXの目的

- 現状：在庫の置き場所はベテラン班長の経験で決めており、出庫頻度が変わっても配置が見直されない。出荷口から遠い棚に高頻度品が残り、歩行距離が長い。
- DXの目的：配置の決め方を「経験則」から「入出庫データに基づく定期的な見直し」に変える。単なる可視化ではなく、「月次の配置見直し会議」という業務を新しく作る点が要(2023講評「単純なIT化をDXとしない」への対策)。
- 情報システム上の課題：既存システムは表形式の一覧しかなく、棚の位置関係や段(高さ)と頻度を結びつけて見る手段がない。

### 検討した複数案と採用理由

| 論点 | 候補 | 採用 | 理由 |
| --- | --- | --- | --- |
| 可視化の手段 | (a) 市販のデジタルツイン製品 (b) 既存WinFormsにWebView2+Three.jsで3D表示を組み込む (c) 2D平面図のヒートマップ | PoCは(c)、本開発は(b) | PoCでは安価な(c)で仮説を検証。その結果、「段の高さ(腰の高さか脚立が必要か)」が作業時間に効いており2Dでは表せないと判明。(a)は既存Oracleのロケーションデータとの連携と年間ライセンス費が課題。(b)は利用者が使い慣れた画面からそのまま開け、社内で改修もできる |
| 配置の決め方 | (a) システムが自動で配置を決定 (b) システムが候補を出し班長が判断 | (b) | 重量物は下段、危険物は指定エリアなどデータ化されていない制約が多い。人とシステムの役割分担を設計した(2015問1でも使える) |

### 工夫(設問ウで使うネタ)

- PoCの仮説：「出庫頻度上位20%の品番を出荷口付近の腰高の段に移せば、ピッキング1件あたりの作業時間が20%以上減る」。判断基準を先に決め、1エリアで2週間試行し、ハンディのスキャン時刻ログで前後を比較した。測定を人手に頼らないことで比較の公平性を保った。
- アジャイル：班長との2週間スプリントで開発。「3Dで倉庫全体を見たい」という大きすぎるUSを、「平面ヒートマップ→段別表示→移動候補の一覧」に分割し、動線短縮への寄与が大きい順に並べた。
- デジタル化で生じる課題：配置を頑繁に変えると「頭で場所を覚えている」ベテランの効率が落ちる。変更は月次に限定し、変更品番を月初に大型モニタで周知、ハンディに「旧棚→新棚」を表示した。
- 性能：約3,000棚を個別の3Dオブジェクトにすると描画が重いため、同形状をまとめて描画する方式(インスタンシング)を採用し、事務所PCでも操作が滑らかになるようにした。

### 使える設問

2023問1(DX)、2022問1(PoC)、2022問2(デジタル化)、2021問1(アジャイル)、2015問1(システム方式)。

## 事例D 生成AIによる品質不具合報告の分類・類似事例検索

「先進技術で人手業務を自動化する」系の切り札です。社内で生成AIが全社導入されている状況をそのまま前提に使え、今年度の出題傾向(新技術の業務適用)にも合います。

### 論述対象の概要(仮値)

| 項目 | 内容 |
| --- | --- |
| 名称 | 生成AIを活用した品質不具合報告の分類・類似事例検索機能の開発 |
| 対象業務 | 生産(品質保証・是正処置) |
| 形態 | クライアントサーバ(DBサーバ1台、APサーバ1台、PC約30台)+外部の生成AIサービス |
| 利用者数 | 約30名(品質保証、製造技術) |
| 工数・期間 | 約10人月・6か月(PoC 1.5か月を含む) |
| 立場 | SAとして適用方針の策定、PoC、方式設計を担当 |

### 業務背景と業務目的

- 対象業務：工程不良や顧客クレームの報告を受け付け、現象・原因の分類コードを付け、過去の類似事例を参考に是正処置を立案する業務。目的は「同じ不具合を繰り返さないこと」(単なる入力作業と書かないこと。2024講評の指摘)。
- 課題：報告は自由記述で、分類と類似事例探しはベテランの記憶に頼っていた。担当者によって分類がばらつき、過去に対策済みの不具合が再発した。
- 大幅な効率化が可能と考えた理由：(1) 過去5年分約8,000件の分類済み報告があり、正解データとして精度を測れる (2) 報告は「現象・発生工程・部位」という観点で書かれており、表現の揺れさえ吸収できれば分類できる (3) 生成AIは言い換えや表記の揺れに強い。

### 検討した複数案と採用理由

| 論点 | 候補 | 採用 | 理由 |
| --- | --- | --- | --- |
| 自動化の手段 | (a) キーワード検索とルール (b) 自前で学習した分類モデル (c) 全社導入済みの生成AI+文章の意味での類似検索 | (c) | (a)はPoCで表記揺れにより正解率が低かった。(b)は分類コードが年数回改定されるたびに再学習が必要で、社内に担い手もいない。(c)は社内のセキュリティ審査を通過済みで、利用枠の範囲で費用も見積もれる |
| AIと人の分担 | (a) AIの分類をそのまま確定 (b) AIは候補を提示し担当者が確定 | (b) | 分類は是正処置と品質統計の基となるため、誤りの影響が大きい。確信度が低いものは「要確認」としてベテランに回す |
| 呼び出し方 | (a) 画面から即時呼び出し (b) 受付登録時にAPサーバで非同期処理 | (b) | 応答に数秒〜十数秒かかり、受付作業を止めたくない。外部サービス障害時も従来の手作業で業務を続けられる |

### 工夫(設問ウで使うネタ)

- PoC：過去1,000件で「上位3候補に正解が含まれる率」を測定し、目標85%を満たすことを本開発の判断基準にした。類似事例はベテラン2名に5段階で評価してもらった。
- 分類コード改定への追従：生成AIへの指示文に含めるコード定義をマスタから毎回生成し、改定時にプログラム修正を不要にした。
- 応答の検証：結果を決めた形式(JSON)で受け取り、存在しないコードが返った場合は「要確認」に振り分けた。
- 機密情報：顧客名や図番は送信前に置き換え(マスキング)、品質保証部長と情報システム部門の合意を得た。
- 効果(仮値)：分類1件約10分→2分、類似事例検索約30分→5分。

### 使える設問

2024問1(先進技術による自動化)、2022問1(PoC)、2018問1(データ活用)。

## 事例E スクラム導入による要件の早期検証(実体験ベース)

実際にやったことなので、一番具体的に書ける事例です。ただし「スクラムを導入した」だけを書くとPM試験の論文になります。SAの論文では、「要件が業務で本当に使えるかを、いつ・どう検証するかを変えた」という軸で書きます。

### 論述対象の概要(仮値、実際の案件に合わせて修正)

| 項目 | 内容 |
| --- | --- |
| 名称 | 変更点管理システムにおける外部データ取込機能・データ編集機能の開発 |
| 対象業務 | 生産(品質管理。工程の変更点を登録・管理する業務) |
| 形態 | クライアントサーバ(.NET Framework 4.8 WinForms、Oracle、PC約30台) |
| 工数・期間 | 約18人月・6か月(3名チーム) |
| 立場 | SAとして要件定義と開発手法の見直しを担当、開発チームを取りまとめた |

### 問題と原因(ここが論文の芯)

- 問題：開発終盤に、要件定義を覆す仕様変更が利用部門から出ることが続いていた。
- 従来の進め方：初期に決めた要件定義を軽に実装し、実装中の疑問点や矛盾は開発側で逐次修正。形になった段階で初めて利用者にフィールドテストを依頼していた。
- 原因の分析：
  - 要件の「業務で使えるか」を利用者が確かめる機会が、フィールドテストの1回しかなかった。
  - 開発途中の修正は開発者目線の整合性の修正に限られ、業務目線の検証がなかった。
  - 初期の要件定義から外れないように無意識に制御しており、要件の誤りが終盤まで表に出なかった。
  - 業務担当者は仕様書や画面イメージでは例外ケース(区分によって必須項目が変わる、など)を思い出しにくく、実データで動かして初めて気づく。

### 検討した複数案と採用理由

| 候補 | 効果 | 採用しなかった/した理由 |
| --- | --- | --- |
| (a) 要件定義を厚くし、画面モックで合意を取る | 画面の見た目の合意は取れる | 業務の例外ケースは動かさないと気づけないため、根本原因に効かない |
| (b) 機能ごとに段階リリースし、フィールドテストを前倒し | 業務での検証が早まる | 1サイクルが1〜2か月と長く、指摘が出たときの手戻りが大きい |
| (c) スクラムで1週間スプリント、毎週利用者がレビュー | 業務目線の検証が毎週入る | 採用。手戻りを最大1週間分に抑えられる。利用部門も「毎週1時間」なら確保できる |

### 工夫(SAらしさを出すポイント)

- 変えにくい部分は初期に固めた：業務目的、データ構造、他機能との連携、非機能要件は最初に合意し、画面・帳票・業務ルールの細部だけをスプリントで詰める。「何でも後から変えられる」にならないように線を引いた。
- 要件をユーザストーリーに書き換えた：「品質担当として、外部ファイルの変更点データを取り込み、不備のある行だけを画面で直したい。取込をやり直さずに登録を終えるため」の形にし、受入基準に業務の例外ケースを入れた。大きすぎるストーリーは1週間でレビューできる大きさに分割した。
- レビューの形式：開発者のデモではなく、利用者が本番データのコピーで自分の業務を操作する形にした。受け身では例外ケースに気づかないため。実際にレビューで、「区分が〇〇ならこの項目も必須」という条件付きの必須チェックが要件定義から漏れていることが見つかった(実例)。論文では、「取込と編集の両方で同じチェックが必要なので、どう共通化して翌週までに反映したか」を実際の対応に合わせて続けて書く。
- 変更要望の扱い：レビューで出た要望はその場では採用せずバックログに積み、業務目的への価値と規模で優先順位を付けた。優先順位の最終判断はPOが行い、レビューに参加する利用者もPOが機能ごとに選んだ。要望の窓口を1人に絞り、範囲が膛らむのを防いだ。
- 評価：初期の作業見積もりと実績の誤差で測る。従来の案件では3か月以上超過していた。ただし見積誤差は仕様変更以外の要因でも動くため、「終盤に出た仕様変更の件数と手戻り工数」も併せて示すと、目的と効果のつながりがはっきりする。残った課題として、毎週のレビューが利用部門の負担になった点などを挙げる。

### 使える設問

2021問1(アジャイルのUSと優先順位)が本命。2021問2(業務要件の分析)、2016問1(優先順位付け)にも転用できる。

### 埋めると強くなる情報

- スクラム導入後の見積誤差(完了前なら、現時点の進捗と見込み)
- 条件付き必須の漏れに対して実際にどう対応したか
- 従来案件で終盤に出た仕様変更のおおよその件数
