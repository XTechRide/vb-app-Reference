## この資料の使い方

この資料は、1つのシステムの企画から稼働後までを16の場面に分けた経験談である。本番ではどの問題が来ても、場面を2〜3個選んで設問ア・イ・ウに並べ替えて書く。

- **文体は論文と同じ**にした(である調・一人称)。読むこと自体が書く練習になる。
- **各場面は同じ型**で書いた。課題 → 案の比較 → 選んだ理由 → 結果 → 残った課題。覚えるのは文章ではなく、この5点である。
- **太字は試験で使える用語**で、初出の場面で意味を説明している。末尾に索引がある。
- **★印は実際の経験と重なる部分**(2層のクライアントサーバ、Oracle、悲観ロック、在庫・品質の業務、スクラムでの開発)。ここは自分の言葉で膨らませやすいので、迷ったら★のある場面を軸にする。

過去10年の採点講評がほぼ毎年指摘しているのは、次の2点である。

1. 実施した事項だけを書き、**理由や検討の経緯が読み取れない**。
2. システムの話に終始し、**業務の目的や特性との関係が書かれていない**。

そのため物語では、どの場面にも「捨てた案とその理由」と「業務側の事情」を必ず入れた。数値は、会社の規模と拠点の数のほかはほとんど出していない。代わりに何を書くかは「数値を使わない表現集」にまとめた。

## 舞台設定

私はソフトウェア開発会社A社のシステムアーキテクトで、産業用ロボットメーカーB社の生産・在庫管理システムの再構築を担当した。

### B社(顧客)

- **事業**：工場の溶接・搬送・組立に使う産業用ロボット(垂直多関節ロボットとその制御装置)の設計・製造・販売・保守。社員は約1,000名である。
- **生産拠点**：国内に3つの工場があり、工場の間は専用線で結ばれている。

  | 工場 | 役割 |
  | --- | --- |
  | 第1工場(本社工場) | ロボット本体の最終組立、出荷検査、出荷。生産管理部、資材部、品質保証部、情報システム部の本拠でもある |
  | 第2工場 | 制御装置の組立と検査 |
  | 第3工場 | アームなどの機械部品の加工と、関節ユニットの組立 |

- **工場間の物の流れ**：第2工場の制御装置と第3工場の関節ユニットを第1工場に送り、本体に組み込む。つまり3工場は、1つの製品を分担して作る関係にある。
- **営業拠点**：国内は仙台、東京、名古屋、大阪、福岡の5都市、海外はアメリカと中国にある。販売と保守サービスの窓口である。
- **製品の特徴**：標準機が中心だが、アーム先端の仕様やケーブル長などを顧客ごとに変える特注機も多い。1台ごとにシリアル番号を持ち、出荷後も長く保守する。
- **生産形態**：減速機やサーボモータのように調達に時間が掛かる部品は需要予測で先に手配し、最終組立は受注後に行う。特注機は受注ごとに製造番号(製番)を採番して部品を手配する。
- **部品の特徴**：部品点数が多く、構成の階層が深い。減速機・サーボモータ・制御基板などの重要部品は、不具合時に追跡できるようロット番号で管理する必要がある。
- **内製品と購入品**：部品には、仕入先から買う購入品と、B社が自社で加工する内製品がある。アームなどの機械部品は、第3工場で素材から加工する。★
- **仕掛品**：加工や組立の途中にある品物を仕掛品という。次の工程をすぐに始めないときは、仕掛品も倉庫の棚に入れて保管する。★
- **4M変更と版**：設計(図面)は変えずに、作り方だけを変えることがある。作業者(Man)、設備(Machine)、材料(Material)、方法(Method)のどれかを変えるので**4M変更**という。B社では、内製品に4M変更があると部品の版(バージョン)を上げる。品目コードは変えない。購入品には版が無く、仕入先で変更があると品目コードそのものが変わる。★
- **経営の方向**：製品を売るだけでなく、故障を未然に防ぐ保守サービスを、国内と海外の両方で収益の柱にしたいと考えている。

## 対象システムの全体像

対象は、受注後の生産計画から部品の手配・受入・保管・組立・出荷までを、3工場を通して扱う「生産・在庫管理システム」である。この1つのシステムを4つの部分に分けて覚える。

### 業務の流れ

1. **計画**：生産管理部が受注と需要予測から、3工場を通した生産計画を立てる。
2. **所要量計算**：製品の部品表を展開し、在庫と発注残を差し引いて、いつ・どの工場で・何を・いくつ手配するかを計算する。
3. **発注**：資材部が仕入先に発注し、仕入先が納期を回答する。部品は、使う工場に直接納められる。
4. **受入**：各工場の倉庫で部品を受け取り、受入検査をして、合格品を棚に入れる。
5. **出庫**：製造指示に従って倉庫から部品を集め、加工や組立のラインに供給する。
6. **製造**：第2工場は制御装置を、第3工場は機械部品の加工と関節ユニットの組立を行う。工程内検査を行い、実績を記録する。次の工程を待つ仕掛品は、いったん棚に入れる。
7. **工場間の移動**：制御装置と関節ユニットを第1工場に送る。送り出してから届くまでの間、その品物は輸送中の在庫になる。
8. **最終組立と出荷**：第1工場で本体を組み立て、出荷検査の後に出荷する。
9. **棚卸**：期末に3工場で一斉に現品を数え、帳簿と照合して在庫金額を会計に渡す。

### 現行システム(再構築前)

★ 長年改修を重ねた、2層のクライアントサーバ型システムである。本社工場にデータベースサーバを置き、3工場の事務所のPCに配布した業務プログラムが、専用線を通ってデータベースに直接接続する。

- 在庫は「工場と倉庫ごとの合計数」しか持たず、どの棚にあるかは担当者の記憶と紙の台帳に頼っていた。
- 入出庫と製造の実績は、紙の伝票を翌日に事務所でまとめて入力していた。
- 工場ごとに、棚の呼び方や伝票の書き方が違っていた。
- 他の工場の在庫は画面で見られるが、現品と合っていないので信用されず、電話で確かめていた。
- ロボット1台にどのロットの部品を組み込んだかは、紙の組立記録にしか残っていなかった。
- 内製品は、版が違っても同じ品目の同じ在庫として扱っていた。版は現品票の表示と、現品票のバーコードや2次元コードで分かるが、システムの在庫には版を持っていなかった。そのため帳簿では新旧の版を区別できず、棚の中でも混ざっていた。版の表示を始める前に作った古い現品には、表示そのものが無い物もある。★
- 仕掛品は品目として登録されておらず、棚に入れた仕掛品は在庫に現れなかった。★
- 所要量計算は夜間に全品目を計算し直す方式で、部品点数の増加とともに処理時間が延びていた。
- ハードウェアと基本ソフトウェアの保守期限が近づいていた。

## 物語 第1部：企画と要件定義

### 場面1 現状調査 ― 「在庫が合わない」の本当の原因

**きっかけ**：B社の情報システム部からの最初の相談は「老朽化した現行システムの更新」だった。しかし私は、更新だけを目的にすると現行の問題をそのまま引き継ぐと考えた。そこで要件定義の最初に、現状の業務を調べることを提案した。

**調査の方法**：3つの方法を組み合わせた。

| 方法 | 内容 | この方法を選んだ理由 |
| --- | --- | --- |
| ヒアリング | 各部門と3工場の責任者と担当者に、困っていることを聞く | 当事者が感じている問題を知る |
| 作業の観察 | 3工場の倉庫と製造ラインで、受入から出庫、組立までの作業を見る | 担当者は長年のやり方を当然と考え、問題として口にしないことがある |
| データの調査 | 現行システムのデータで、伝票の日付と入力された日時のずれなどを調べる | 「遅れている」という感覚を事実で確かめる |

3工場の全てを見たのは、本社工場で聞いた話が他の工場にも当てはまるとは限らないからである。

**分かったこと**

観察では、応援の作業者が部品を探せず、ベテランを呼びに行く場面を何度も見た。ベテランは自分の出庫を中断して案内していた。ヒアリングでは誰もこれを問題に挙げなかった。昔からそうだからである。

★ データの調査では、入出庫の大半が、伝票の日付の翌日以降に入力されていることを確かめた。月末は入力がさらに遅れていた。また、在庫数がマイナスになっている品目があった。出庫の伝票が、入庫の伝票より先に入力されたためである。マイナスの在庫は、帳簿が現品の動きを追えていないことの証拠だと私は考えた。

調査結果は**As-Is**(現状の姿)の**業務フロー**(誰が・どの順で・何を使って作業するかを図にしたもの)にまとめた。すると、部門や工場ごとに別々に語られていた問題が1つにつながった。

- **各工場の倉庫**：部品の置き場所が記録されておらず、探すのに時間が掛かる。棚の呼び方が工場ごとに違うので、工場をまたぐ応援は特に難しい。
- **生産管理部**：システム上の在庫が現品と合わない。所要量計算の結果を信用できず、担当者が手元の表計算ソフトで余裕を上乗せして発注していた。その結果、ある工場で欠品している部品が別の工場では余っている、ということが起きていた。
- **第1工場の組立**：第2・第3工場から届くはずの制御装置や関節ユニットが、今どこにあるのか分からない。届くまで組立の段取りが決められない。
- **品質保証部**：出荷後に部品の不具合が分かったとき、そのロットを組み込んだロボットを特定するのに、3工場の紙の記録を1枚ずつ確認していた。

**原因の判断**：私は、これらの原因は「現品が動く場所・時刻と、情報を記録する場所・時刻が離れていること」にあると判断した。倉庫で動いた部品が、翌日に事務所で記録される。この間、システムは事実と違う数を示し続ける。

**基本方針**：**To-Be**(あるべき姿)の基本方針を「現品が動いたその場で、その時に記録する。その記録を3工場で同じ形で持つ」と定めた。To-Beの業務フローを作り、3工場の責任者と一緒に確認した。

**現場の反対と対応**：倉庫の責任者からは「作業のたびに入力するのでは手間が増える」という反対が出た。私は、現在の作業を一緒に数えた。部品を出す、伝票に品番と数を書く、伝票を事務所に運ぶ、事務所で入力する。新しい方法では、部品を出すときに棚と現品票を読み取るだけになり、伝票を書く作業と事務所での入力がなくなる。作業の数が減ることを示して、理解を得た。

**経営の方向との関係**：B社が目指す予防保全のサービスは、「どのロボットにどのロットの部品が入っているか」が分からなければ成り立たない。このように製品と部品の履歴を後からたどれることを**トレーサビリティ**という。つまりシリアル別の部品記録は、品質保証部の作業を楽にするだけでなく、新しい事業の前提になる。私はこの点を生産担当役員に説明し、再構築の目的を「更新」から「**DX**(デジタル技術で業務や事業そのものを変えること)の土台づくり」に改めることで合意した。

**私が意識したこと**：**業務要件**(業務で実現したいこと)と**システム要件**(そのためにシステムが備えること)を分けることである。「ハンディ端末を入れたい」は手段であり、業務要件は「出庫したその場で在庫が減ること」である。手段から入ると、端末を入れたのに事務所での入力が残る、といった結果になりかねない。

### 場面2 要求の優先順位付け ― 声の大きさで決めない

**課題**：3工場と各部門から多くの要求が出た。同じ業務でも工場によって要求が違うこともあった。しかし現行システムの保守期限までに稼働させる必要があり、全ては実現できない。要求を出した人は皆、自分の要求が重要だと考えている。決め方が見えないと、採用されなかった部門に不満が残る。

**手順**

1. 要求を業務要件の単位に整理する。重複をまとめ、手段で語られた要求は目的に戻す。
2. 評価項目を決める。
3. 評価項目に重みを付ける。
4. 各部門と各工場の代表者と一緒に評価する。
5. 結果を一覧にして生産担当役員が決定する。

手順1が最も手間が掛かった。例えば「在庫の一覧をCSVで出したい」という要求の目的を聞くと、「他の工場に余っている部品を探したい」だった。それなら必要なのはCSVではなく、3工場の在庫を横に並べて見られる画面である。目的に戻すと、別々に見えた要求が1つの業務要件にまとまることが多かった。

**評価項目と重み**

| 側 | 評価項目 | 見る内容 |
| --- | --- | --- |
| 効果 | 開発目的への寄与 | 「その場で記録する」「3工場で同じ形で持つ」に効くか |
| 効果 | 効果が及ぶ範囲 | 1つの工場だけか、3工場か。1つの部門だけか、複数か |
| 効果 | 緊急性 | 稼働の時点で無いと業務が回らないか |
| 負担 | 実現の難しさと費用 | 開発の規模、他の機能への影響 |
| 負担 | 現場の作業が変わる大きさ | 教育や習熟にどれだけ掛かるか |

各項目は高・中・低の3段階で評価した。重みは「開発目的への寄与」を最も重くした。理由は、部門や工場の声の大きさで決めると、目的に効かない便利機能が先に入ってしまうからである。評価の基準を先に決めて合意してから個々の要求を評価したことも、工夫の1つである。個々の要求を見てから基準を決めると、基準が特定の要求に有利になるように引っ張られる。

**評価の結果**：**MoSCoW**(必須・できれば実現・余裕があれば実現・今回は見送りの4段階に分ける方法)で分類した。

| 業務要件 | 判定 | 理由 |
| --- | --- | --- |
| 棚番別に在庫を管理する | 必須 | 開発目的に直結し、他の要件の前提になる |
| 工場間で輸送中の品物を把握する | 必須 | 第1工場の組立の段取りに欠かせない。3工場の全てに効果が及ぶ |
| シリアル別に部品ロットを記録する | 必須。ただし重要部品に限る | 事業の前提である。全部品を対象にすると作業者の読取りの負担が大きい |
| 内製品は、同じ部品でも版が違えば区別して追跡する | 必須。ただし所要量計算と発注では同じ部品として扱う | 版を区別できないと、不具合の範囲を絞り込めない。一方、設計は同じなので、計画まで別の部品にすると在庫が分かれてしまう(場面6) |
| 棚に入れた仕掛品を在庫として管理する | 必須。ただし棚に入れる物に限る | 棚にあるのに帳簿に無い物が残ると、開発目的の「現品と帳簿の一致」が成り立たない(場面6) |
| 仕入先の納期回答をオンライン化する | できれば実現。第2期へ | 効果は大きいが、仕入先側の準備が必要で稼働時期に合わない |
| 第3工場だけで使っている独自の加工日報をそのまま画面にする | 今回は見送り | 1つの工場だけの要求で、開発目的への寄与が小さい。共通の実績入力で必要な情報は取れる |
| 組立作業の日程を自動で組む | 今回は見送り | 前提となる作業ごとの標準時間のデータが整っていない |

**意見が割れた場面**：シリアル別の部品ロットの記録は、品質保証部が「全部品」を求め、製造課が「組立の手が止まる」と反対した。私は、過去の市場不具合で追跡が必要になった部品を品質保証部と調べ、減速機、サーボモータ、制御基板などの重要部品に集中していたことを示した。対象を重要部品に限れば、品質保証部の目的の大半を満たしつつ、製造課の負担を抑えられる。両者はこの案で合意した。

**見送る要件の扱い**：日程の自動作成は生産管理部の強い要望だった。私は「見送り」とだけ伝えると納得が得られないと考え、「新システムで製造実績を収集すれば標準時間が蓄積される。データが整った段階で着手できる」と、着手の条件を添えて合意した。

**結果の残し方**：評価の結果は、理由と一緒に一覧表に残した。設計の途中で要求の追加や変更が出たとき、同じ基準で評価し直すためである。実際に、設計の途中で出た追加要求の多くを、この表を使って第2期に回すことができた。

### 場面3 3工場の業務手順の統一 ― 現行のままか、そろえるか

**課題**：場面1の調査で、同じ業務でも工場ごとに手順が違うことが分かった。

| 業務 | 第1工場 | 第2工場 | 第3工場 |
| --- | --- | --- | --- |
| 受け入れた部品の扱い | 検査が済むまで専用の置き場に置く | 検査の前に棚に入れ、札で区別する | 検査の前に棚に入れ、札で区別する |
| 出庫の単位 | 製造指示1件ごとに出庫する | 1日分をまとめて出庫する | 製造指示1件ごとに出庫する |
| 棚の呼び方 | 列と段の番号 | 部品の種類の名前 | 担当者ごとの呼び名 |

このままシステム化すると、工場ごとに別の画面と処理が必要になる。

**案の比較**

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A 現行の手順のまま工場別に作る | 工場ごとに画面と処理を分ける | 現場の作業は変わらない | 開発と保守が3倍になる。工場をまたぐ応援や、在庫を3工場で同じ形で見ることができない |
| B 第1工場の手順に統一する | 最も規模の大きい工場のやり方に合わせる | 決めるのが早い | 他の工場の事情(置き場の広さ、製品の違い)を無視することになり、守られない恐れがある |
| C 業務の目的から共通の手順を決め、工場固有の事情だけを設定で切り替える | 手順ごとに「何のためにそうしているか」を確かめ、目的が同じなら手順をそろえる | 処理は1つで済む。固有の事情にも対応できる | 3工場の合意に時間が掛かる |

私は案Cを選んだ。基本方針の「3工場で同じ形で持つ」を満たし、かつ守られる手順にするには、各工場の事情を聞いた上でそろえる必要があるからである。

**進め方**：3工場の倉庫の責任者に集まってもらい、手順の違いを1つずつ取り上げた。

- **受け入れた部品の扱い**：目的は「検査に合格していない部品を使わせないこと」で、3工場とも同じだった。置き場を分けるか札で区別するかは手段の違いである。新システムでは、在庫に「検査待ち」の状態を持たせ、検査待ちの部品は出庫の読取りで止める。これなら置き場の広さに関係なく、3工場で同じ目的を達成できる。
- **出庫の単位**：第2工場がまとめて出庫するのは、小さな電子部品が多く、1件ごとに出すと手間が大きいからだった。これは工場の事情として妥当である。出庫の単位を「製造指示ごと」と「まとめ」から工場と品目の区分ごとに選べる設定にした。
- **棚の呼び方**：目的は「誰でも場所が分かること」である。担当者ごとの呼び名はこの目的を満たさない。3工場で「工場・区画・列・段」の共通の棚番にそろえた。

**設計変更の切替の扱い**：手順の違いとは別に、3工場に共通する独特の運用があった。設計変更で部品が変わるとき、B社では「旧部品の在庫を使い切ってから新部品に切り替える」ことが多い。高価な部品を無駄にしないためである。私は所要量計算での切替の方法を3案で比較した。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A 日付で切り替える | 切替日を決め、その日から新部品で計算する | 仕組みは単純だが、旧部品が残れば廃棄損が出る。切替日を担当者が見積もる必要がある |
| B 使い切りで切り替える | 旧部品の在庫と発注残が無くなった時点から、新部品で計算する | 旧部品を無駄にしない。ただし安全上の理由で直ちに切り替えるべき設計変更には使えない |
| C 設計変更ごとに方法を選ぶ | 設計変更の登録時に、日付切替か使い切り切替かを指定する | 両方の場合に対応できる。処理は増える |

私は案Cを選んだ。設計変更には、費用を重視してよいものと、品質や安全のためにすぐ切り替えるべきものがあり、1つの方法では業務の実態に合わないからである。どちらを選ぶかは、設計変更を起こす設計部が指定することにした。

**振り返り**：適切だった点は、手順をそろえたことで、画面と処理が3工場で1つになり、稼働後の改修が1か所で済んでいることである。改善の余地がある点は、まとめ出庫の設定を認めたことで、第2工場ではライン側に出庫済みの部品がたまり、その数が見えにくくなったことである。ライン側の在庫を棚として登録する運用で補っている。

### 場面4 非機能要件 ― 役員に「業務の言葉」で選んでもらう

**機能要件**はシステムが何をするか、**非機能要件**はそれをどの程度の品質で行うか(止まらないこと、速さ、安全性など)を定めるものである。非機能要件は利用者から要求として出にくく、漏れると稼働後に大きな障害につながる。

**検討のプロセス**

1. **業務の視点**：業務ごとに「止まると何が起きるか」「いつ処理が集中するか」を洗い出す。
2. **情報システムの視点**：IPAの**非機能要求グレード**(可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境の6つの大項目で要求を整理する枠組み)を用いて、検討項目の漏れを防ぐ。
3. 両方を突き合わせ、機能ごとに要求の水準を決める。
4. 水準の案と費用を意思決定者に示し、選んでもらう。

**業務の視点で分かったこと**

| 業務 | 止まったときの影響 | 処理が集中する時 |
| --- | --- | --- |
| 倉庫の出庫 | ラインに部品が届かず、製造が止まる。第2・第3工場が止まれば、やがて第1工場の最終組立も止まる | 始業の直後 |
| 受入と受入検査 | 部品が棚に入らず、後の出庫に影響する。半日程度なら置き場で待てる | 仕入先の便が着く午前 |
| 事務所の計画業務 | 半日止まっても翌日に取り戻せる | 月末と期末 |
| 所要量計算 | 翌朝の発注の判断ができない | 夜間 |

**検討した結果**

- **可用性**(必要なときに使える度合い)：水準を全体一律にせず、現場系だけを高くする方針を立てた。一律に高くすると、必要のない部分にまで費用が掛かるからである。障害から復旧するまでの目標時間である**RTO**と、どの時点のデータまで戻せればよいかを示す**RPO**を、機能のまとまりごとに定めた。
- **性能**：「応答時間は何秒」と決める前に業務の場面で表した。ハンディ端末は「読み取った後、作業者が次の部品に手を伸ばすまでに結果が出ること」、所要量計算は「資材部の始業時に結果が出そろっていること」である。その上で、始業直後の出庫の集中を前提に、同時に操作する端末の数を工場ごとに見積もった。
- **セキュリティ**：検査記録と部品ロットの記録は、後から書き換えられると追跡の根拠を失う。確定した記録は訂正の履歴を残す方式にした。
- **運用・保守性**：情報システム部は少人数である。夜間バッチの結果を朝に1つの画面で確認できることを要件にした。

**意思決定者への説明の工夫**：水準を決めるのは、費用を負担する生産担当役員である。しかし「サーバを冗長化する」といった技術の言葉では判断できない。私は3つの工夫をした。

第一に、要求の水準を業務への影響で表した。「障害時に出庫作業が止まる長さ」と「その間に止まる工場とラインの範囲」である。

第二に、水準の異なる3つの案を作り、費用と、採用しても残るリスクを並べて示した。

| 案 | 内容 | 障害時の業務 | 残るリスク |
| --- | --- | --- | --- |
| 1 | サーバは1台ずつ | 機器を交換するまで3工場とも紙の伝票で作業する | 復旧に日数が掛かる場合がある |
| 2 | 現場系に関わるサーバを2台構成にし、片方が壊れたら自動で切り替える | 作業はほぼ止まらない | サーバ室そのものが使えなくなる災害には対応できない |
| 3 | 案2に加え、別の工場に予備のシステムを置く | 本社工場が被災しても他の工場は作業を続けられる | 費用が最も大きい |

第三に、私が推奨する案とその理由を明示した。推奨は案2である。機器の故障は現実に起こるが、サーバ室が使えなくなるほどの災害では工場の製造そのものが止まるので、システムだけを動かし続ける意味が小さいと考えた。

**決定**：役員は案2を選んだ。災害への備えとして、バックアップのデータを第2工場に保管することを加えた。さらに、システムが止まっている間は紙の出庫伝票で作業を続け、復旧後にまとめて入力する「代替運用」も、要件として定めた。

## 物語 第2部：方式設計と外部設計

### 場面5 システム方式設計 ― 2層をやめる理由、集中させる弱点の補い方

**システム方式設計**とは、システム要件をハードウェア、ソフトウェア、人手による作業のどれで実現するかを決める設計である。私は4つの点を決めた。

**(1) サーバの構成**

★ 実現したいシステム要件は3つである。3工場の在庫を1つの形で持つこと、ハンディ端末・タブレット・PC・社外の仕入先という種類の違う端末から使えること、出庫を止めないことである。私は次の3案を比較した。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A 2層のクライアントサーバ | 現行と同じ。端末に業務プログラムを配布し、専用線を通って本社工場のデータベースに直接つなぐ | 開発者も利用者も慣れている | 端末の種類が増えると配布と更新の手間が増える。在庫更新などの処理を端末の種類ごとに重複して持つ。社外の仕入先にデータベースを直接つながせることはできない |
| B 3層のWebシステムを本社工場に集中して置く | 業務処理とデータベースを本社工場のサーバ室に置く。第2・第3工場は専用線を通って使う | 在庫を1か所で持てる。業務処理が1か所にまとまる。既存の専用線を活かせる | 本社工場のサーバや専用線の障害で、他の工場まで止まる |
| C 3層のWebシステムを工場ごとに分散して置く | 3工場のそれぞれにサーバとデータベースを置き、互いにデータを同期する | 各工場が単独で動ける | データベースが3つに分かれ、同期の遅れで工場間の在庫が食い違う。輸送中の品物のように、2つの工場にまたがるデータの扱いが複雑になる |

**3層構成**とは、画面を受け持つ層、業務処理を受け持つ層、データを受け持つ層に分ける構成である。在庫更新のような業務処理をサーバ側1か所にまとめられるので、PC・ハンディ端末・タブレット・仕入先ポータルのどこから操作しても、同じ規則で処理される。端末にはブラウザか小さな画面用のプログラムがあればよく、業務の規則が変わってもサーバ側だけを直せば済む。

案Aは、端末の種類が増えることと社外からの利用に対応できないので、採用できないと判断した。現行システムの改修で、プログラムの配布漏れのために工場によって動きが違う、という障害を私自身が経験していたことも理由である。

案Bと案Cの比較では、場面1で定めた基本方針「記録を3工場で同じ形で持つ」を重く見た。案Cは止まりにくいが、在庫が3つのデータベースに分かれ、現行の「他の工場の在庫が信用できない」という問題を形を変えて残してしまう。私は案Bを選んだ。

ただし案Bには、本社工場のサーバや専用線が止まると他の工場まで止まるという弱点がある。場面4で定めたとおり、出庫の停止は製造の停止に直結する。そこで私は、弱点を4段階で補った。

1. 現場系に関わるサーバを2台構成にし、片方が壊れたら自動で切り替える(**冗長化**：予備を持たせて、1つが壊れても止まらないようにすること)。
2. 工場間の専用線が切れたときのために、別の経路の予備回線を用意し、自動で切り替える。
3. ハンディ端末は、通信できない間も読取り結果を端末内に一時保存し、通信が回復したら送信する。
4. それでも使えない場合は、紙の出庫伝票による代替運用に切り替える。

4つ目はハードウェアでもソフトウェアでもなく、人手による作業で要件を満たす部分である。全てを機械で解決しようとすると費用が際限なく増える。めったに起きない事態は人手で受ける、という割り切りを役員と合意した。

**(2) 現品を識別する方法**

「その場で記録する」ためには、作業者が簡単に部品と棚を識別できなければならない。

| 方法 | 評価 |
| --- | --- |
| 品番の手入力 | 桁数が多く誤りが出る。手袋をした作業者には負担が大きい |
| **RFID**(電波を使い、離れた位置から複数の荷札をまとめて読み取る技術) | 一括で読める点が魅力である。しかしB社の倉庫は金属の部品と金属の棚が多く、電波が反射して読取りが安定しない恐れがある。荷札の費用が部品の容器ごとに掛かる |
| 2次元コード | 品目・版・ロット・数量を1つのコードに入れられ、現品票に印字するだけで済む。1つずつ読む必要がある |

私は、確実に読めることを優先して2次元コードを選んだ。出庫では、どのみち作業者が1つずつ部品を手に取る。一括で読める利点は、B社の出庫作業では生きにくいと考えた。現品票は、受入のときに倉庫で印刷して貼る。第2期からは、仕入先が仕入先ポータルで印刷して貼ってから納める。工場間で送る制御装置と関節ユニットにも同じ現品票を付け、送り出しと受け取りの両方で読むことにした。

**(3) 同時更新の制御**

★ 現行システムは**悲観ロック**(更新画面を開いた時点でデータをロックし、他の人を待たせる方式)である。事務所の少人数が使う分には問題なかった。しかし現場の端末では、画面を開いたまま作業者が端末を置いて離れることがある。ロックが残ると、他の作業者が同じ棚の部品を出庫できなくなる。現行システムでも、席を外した担当者のロックを解除してほしいという依頼が情報システム部に寄せられていた。

そこで現場系は**楽観ロック**(画面を開いた時点ではロックせず、更新する瞬間に、読んだ後で他の人が更新していないかを確かめる方式)を基本にした。確かめる方法として、各行に更新回数の項目を持たせ、読んだときの回数と更新するときの回数が同じかを見る。

さらに在庫数は、「現在の数を読み、計算して書き戻す」のではなく、「いくつ減らす」という差分で更新することにした。こうすれば、2人が同じ棚の同じ部品を同時に出庫しても、両方の結果が正しく反映され、やり直しも起きない。差分で引いた結果がマイナスになる場合だけ、エラーにする。

一方、品目などのマスタを保守する画面は、事務所で少人数が使う。長い入力の後で「他の人が更新したのでやり直し」となるより、編集の衝突を先に知らせた方が親切である。こちらは悲観ロックのままにし、一定の時間操作が無ければロックを自動で外すようにした。

**(4) 利用者への説明**

方式は目に見えないので、文書で説明しても現場の責任者には伝わりにくい。私は2つの工夫をした。第一に、業務フロー図の上に「どの作業でどの端末を使うか」「通信が切れたらどの作業が続けられるか」を重ねた図を作った。第二に、試作した端末を倉庫に持ち込み、無線が届きにくい棚の奥で、通信が切れても読取りを続けられ、戻ると送信される様子を実演した。

実演の結果、現場の責任者から「一時保存している間に端末の電池が切れたらどうなるか」という質問が出た。これは説明が理解されたからこそ出た質問である。私はこれを受け、一時保存のデータを電源が切れても消えない領域に置くことを要件に追加した。実演は3工場のそれぞれで行った。無線の届き方も倉庫の造りも、工場ごとに違うからである。第3工場では、加工機械の近くで無線が不安定になることが実演で分かり、無線の中継機の位置を見直した。

### 場面6 データ設計と他システム連携 ― 相手の都合で止まらないようにする

**(1) 在庫の持ち方**

★ 現行は「品目・工場・倉庫」ごとに残高を1行持つだけだった。新システムでは次の2つの表を中心にした。

| 表 | 1行が表すもの | 主な項目 |
| --- | --- | --- |
| 在庫残高 | ある品目の、ある棚にある、ある版の、あるロットの、ある状態の在庫 | 品目、工場、棚番、版、ロット、状態、在庫数、引当済みの数、更新回数 |
| 受払履歴 | 入庫・出庫・移動・状態の変更の1件 | 日時、種類、品目、版、ロット、移動元と移動先の棚、数量、製造指示の番号、作業者、端末 |

状態とは、検査待ち・良品・保留・輸送中の区別である。検査待ちと保留を設けたのは、検査に合格していない部品を出庫できないようにするためである。輸送中を設けたのは、工場間で送り出した品物が、届くまでどの工場の在庫でもなくなって見えなくなることを防ぐためである。

受払履歴は消さず、訂正も「取消の1件」と「正しい1件」を追加する方式にした。残高は履歴の積み上げと常に一致させる。残高だけでは「なぜその数になったか」をたどれず、棚卸で差異が出たときに原因を調べられないからである。現行システムでは残高を直接書き換える修正ができたため、差異の原因が分からなくなっていた。

ロットの単位で在庫を持つと、行数は現行よりはるかに増える。私は、棚の出庫で使う検索(棚と品目から在庫を引く)と、追跡で使う検索(ロットから在庫と履歴を引く)の2つが速く動くことを、設計の段階で試作して確かめた。

**(2) 3種類の部品表**

設計部が機能の観点で作る部品表を**設計部品表(E-BOM)**、それを製造の順序や工程の観点で組み替えたものを**製造部品表(M-BOM)**という。製造部品表には、どの部品をどの工場で作るかも含まれる。計画系は設計部品表管理システムから設計部品表を受け取り、製造部品表を持つ。これとは別に、現場系は「実際にその1台に組み込んだ部品とロット」を記録する。計画上の部品表と実際の構成は、代替部品の使用や設計変更の切替で食い違うことがある。保守サービスに必要なのは実際の構成の方である。

**(3) 版の違う部品の扱い ― 計画では同じ物、追跡では別の物** ★

**背景**：B社では、内製品に4M変更があると版を上げるが、現行システムは版が違っても同じ物として扱っていた。設計が同じで、どの版でも組み付けられるからである。購入品は事情が違い、仕入先で変更があると品目コードが変わるので、もともと別の物として区別できていた。区別できないのは内製品だけだった。

しかし品質保証部は困っていた。不具合の原因が「ある版からの作り方の変更」だと分かっても、その版の部品がどの棚に残っているか、どのロボットに入っているかを調べられない。結局、その部品を使った全てのロボットを対象にして調べるしかなかった。品質保証部は「版が違えば別の物として扱いたい」と要望した。

一方、生産管理部と資材部は反対した。版ごとに別の部品にすると、所要量計算で在庫が版ごとに分かれ、合計では足りているのに不足と計算される。版が上がるたびに部品表を書き換える作業も生じる。

私は、両者の言い分はどちらも正しく、「別の物として見たい場面」と「同じ物として見たい場面」が業務によって違うのだと整理した。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A 版ごとに品目コードを分ける | 版が上がるたびに新しい品目を登録する | 追跡は確実である。仕組みが単純 | 所要量計算と発注で在庫が分かれる。設計は変わっていないのに、版のたびに部品表を変える必要がある |
| B 品目コードは同じにし、版を在庫の属性として持つ | 在庫残高、受払履歴、シリアル別の記録に版の項目を持つ | 計画は品目で合算し、現場と追跡は版で区別できる | 在庫の行が増える。機能ごとに「版を見るか、見ないか」を決める必要がある |
| C 版は持たず、ロットと版の対応表だけを持つ | 追跡のときに、ロットから版を調べる | 変更が最も小さい | 棚や出庫の時点で版が分からず、新旧が混ざることを防げない。内製品は、ロットの切れ目と版の切れ目が一致しないことがある |

私は案Bを選んだ。案Aは購入品と同じ扱いにそろえる案で、分かりやすい。しかし購入品は仕入先の型番が変わるので、発注でも区別が必要である。内製品は図面も作る場所も同じで、計画の上で区別する理由が無い。案Aは品質保証部の要望に最も素直に応えるが、設計が同じ物を別の品目にすると、設計部品表と製造部品表が版のたびに食い違い、生産管理部と資材部の業務を壊す。案Cは追跡の調べ方を楽にするだけで、「棚で混ざる」という原因に手が届かない。案Bなら、1つのデータで両方の見方に応えられる。

**機能ごとの版の扱い**：案Bの短所である「見るか、見ないか」は、機能ごとに利用部門と決めた。

| 機能 | 版の扱い | 理由 |
| --- | --- | --- |
| 所要量計算、発注 | 版を区別せず、品目で合算する | どの版でも組み付けられるので、足りるかどうかは合計で決まる |
| 棚入れ、在庫照会、棚卸 | 版ごとに分ける | 現品がどの版かを、棚の単位で分かるようにする |
| 出庫 | 古い版から先に出す。同じ版の中では古いロットから出す | 新旧が混ざる期間を短くする |
| シリアル別の部品記録 | 版とロットの両方を記録する | 不具合の範囲を版で絞り込む |
| 品質指標(場面14) | 版ごとにも集計できる | 4M変更の前後で故障の出方が変わったかを確かめる |

**工夫した点**

- **作業者に版を入力させない**：内製品の現品票には、すでに版がバーコードや2次元コードで入っている。新システムは、棚入れ・出庫・組立の読取りのときに、このコードから版を取り込む。新しく作る内製品は、加工の実績を登録したときに現品票を発行するので、その時点で有効な版が自動で入る。版を手で入力させると、入力の誤りがそのまま追跡の誤りになるからである。
- **混ぜて使ってよいかを変更ごとに指定する**：4M変更には、新旧を混ぜて使ってよいものと、旧版をすぐに止めるべきものがある。そこで4M変更の登録時に、品質保証部が「混ぜて使ってよい」「旧版を使い切ってから切り替える」「旧版は使用停止」のどれかを指定するようにした。使用停止の版は、出庫の読取りで止まる。場面3の設計変更の切替と同じ考え方である。
- **版を登録する責任を決める**：製造課が4M変更を申請し、品質保証部が承認するときに版を登録する。登録が現品の切替より遅れると、新しい版の現品に古い版の現品票が付く。そのため、登録は適用の開始より前に行う手順にした。

**残った弱点**：版の表示を始める前に作った古い現品には、現品票に版が無い。これは読取りでは区別できないので、「版不明」という版として登録することにした(場面12)。推定で版を埋めると、追跡の結果を誤らせるからである。版不明の在庫は先に出庫して使い切り、新たに増えないようにした。

**(4) 仕掛品の扱い ― 棚に入れる物だけを在庫にする** ★

**課題**：第3工場の加工品や関節ユニットは、工程の途中で次の工程を待つ間、倉庫の棚に入れられる。しかし現行システムには部品と製品の品目しか無く、仕掛品は帳簿に現れなかった。その結果、次の3つが起きていた。

- 棚卸のたびに「帳簿に無い現品」が見つかり、扱いを人が判断していた。
- 仕掛品を置いた棚を担当者しか知らず、探すのに手間が掛かっていた。
- 所要量計算が仕掛品の存在を知らないので、すでに途中まで作った物があるのに、新たに作る指示が出ていた。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A 全ての工程の仕掛品を在庫にする | 工程ごとに中間の品目を設け、工程を進むたびに入出庫を記録する | 最も正確である | ラインの上にある物まで読取りが必要になり、作業者の記録の手間が大きく増える |
| B 棚に入れる仕掛品だけを在庫にする | 棚に入れる区切りの工程にだけ、中間の品目を設ける。ラインの上にある物は、製造指示の進み具合で把握する | 記録の手間が増えるのは、もともと棚に運ぶ作業のときだけ | どの工程を区切りにするかを、あらかじめ決めておく必要がある |
| C 仕掛品は在庫にしない | 製造指示の進み具合だけで把握する | 変更が小さい | 棚の場所が分からず、所要量計算にも反映できない |

私は案Bを選んだ。課題の原因は「棚にあるのに帳簿に無い」ことであり、ラインの上にある物まで在庫にする必要は無い。案Aは正確だが、開発目的である「その場で記録する」を現場が続けられなくなるおそれがあった。

- **区切りの工程の決め方**：製造部品表に、棚に入れる区切りの工程だけ中間の品目(中間品)を登録した。どこを区切りにするかは、第3工場の製造課と、実際に棚へ運んでいる工程を確かめて決めた。
- **部品と同じ画面で扱う**：仕掛品の棚入れと出庫は、部品と同じハンディ端末の画面を使う。作業者が新しい操作を覚えなくて済む。
- **所要量計算への反映**：中間品の在庫は、所要量計算で差し引く。途中まで作った物があれば、その先の工程の指示だけが出る。
- **ロットと版を引き継ぐ**：内製品は、素材のロットと、加工した仕掛品のロットのつながりを受払履歴に記録する。不具合が素材によるものか、加工によるものかを切り分けられる。
- **会計への渡し方**：品目に、購入品・内製品・仕掛品・製品の区分を持たせ、会計システムに渡す在庫金額を区分ごとに集計できるようにした。

**(5) 連携の方式**

| 方式 | 内容 | 向く場面 |
| --- | --- | --- |
| データベースの直接参照 | 相手のデータベースを直接読む | 作るのは簡単だが、相手の構造が変わるとこちらが動かなくなる |
| ファイル連携 | 決まった時刻に、データをファイルにまとめて受け渡す | 即時性が要らず、件数が多いもの |
| API連携 | 必要なときに、決められた窓口を1件ずつ呼び出す | 即時性が要るもの |

私は、直接参照はどの連携にも使わないと決めた。システム同士が相手の内部に依存する**密結合**になり、一方の改修が他方の障害になるからである。現行システムでは、販売管理システムが在庫の表を直接読んでおり、在庫の表を直せないことが改修の足かせになっていた。受け渡す項目と形式だけを取り決め、内部には立ち入らない**疎結合**を方針にした。

その上で、方式は業務が必要とする鮮度で選んだ。

| 相手 | 内容 | 方式 | 理由 |
| --- | --- | --- | --- |
| 会計システム | 在庫金額、仕入実績 | 月次のファイル連携 | 月に1度で足りる |
| 設計部品表管理システム | 設計部品表、設計変更 | 1日1回のファイル連携 | 設計変更は当日中に反映されれば足りる |
| 販売管理システム | 受注、出荷実績、生産の進み具合 | 受注はAPI連携、実績は1日数回のファイル連携 | 営業拠点は受注の直後に納期の見込みを知りたい |
| 保守サービスシステム | ロボットに入っている部品の照会 | API連携 | 営業拠点の保守担当が修理の受付中に答えを必要とする。海外の拠点からも呼び出されるので、時刻を問わず応答する |

**連携の失敗への備え**：ファイル連携では、ファイルの最後に件数と合計を付け、受け取った側が照合する。途中で切れたファイルを取り込まないためである。API連携では、相手が止まっていても自分の業務が止まらないように、受注の取り込みはいったん受け付けて後で処理する形にした。

**(6) コードの違い**

保守サービスシステムの補修部品コードと、本システムの品目コードは別の体系だった。どちらかに統一するのが理想だが、両方のシステムと帳票、営業拠点の手順書に影響が及ぶ。私は、両者を対応づける変換表を本システム側に持つことにした。変換表は作って終わりではなく、新しい部品が増えるたびに保守が要る。そこで、保守の責任部門を品質保証部と決め、対応が未登録のコードを一覧で確認できる画面を用意した。

### 場面7 倉庫のハンディ端末の画面設計 ― 手袋をした応援者が迷わないこと

**利用者の特性と利用シーン**

| 利用者 | 特性 |
| --- | --- |
| ベテランの倉庫作業者 | 部品と棚を知り尽くしている。速く作業したい。画面の案内は不要 |
| 応援者と新人 | 繁忙期に他の職場や他の工場から来る。部品の名前も棚の場所も知らない。端末は初めて使う |

利用シーンは共通である。手袋をし、片手に部品や容器を持ち、立ったまま移動しながら操作する。棚の奥は暗く、周囲には機械の音がある。画面をじっと見ていられる時間は短い。

**重視したユーザビリティ**：**ユーザビリティ**とは、特定の利用者が特定の状況で目的を達成するときの、有効性(正しくやり遂げられること)、効率(少ない手間でできること)、満足度の度合いである。私は有効性を最も重視した。誤った部品がラインに渡ると品質問題になり、在庫のずれにもつながるからである。その次に効率を重視した。出庫は1日に何度も繰り返す作業で、1回の小さな手間が積み重なるからである。

**出庫の画面の流れ**

1. 端末が、次に出庫する製造指示と、最初に行く棚を表示する。行く順番は、倉庫の中を一筆書きで回れる順に並べる。
2. 作業者が棚の2次元コードを読む。指示と違う棚なら、音と赤い画面で知らせる。
3. 作業者が部品の現品票を読む。品目が違う場合、検査待ちの場合、指示より新しいロットを取ろうとした場合は止める。
4. 数量を確認する。指示の数が初期表示されているので、合っていれば確定を押すだけである。
5. 次の棚を表示する。全ての部品が済んだら、供給先のラインを表示する。

**設計の要点**

- **1画面1作業**：画面には次に行う動作を1つだけ表示する。応援者が迷わないためである。
- **読取りが中心**：キーで入れるのは数量だけにした。
- **色と音と振動で結果を知らせる**：画面を見続けられず、周囲がうるさい状況に合わせた。正常と異常で音の種類を変えた。
- **誤りはその場で止める**：人が誤っても事故にならないようにするこの考え方を**フールプルーフ**という。
- **棚に部品が無いときの出口**：指示された棚に部品が無いこともある。そのとき作業者が先に進めなくなることを避けるため、「この棚に無い」と報告するボタンを設けた。報告すると、同じ品目の別の棚を案内し、倉庫の責任者に通知する。
- **ベテラン向けの連続読取り**：確認の画面を省き、続けて読めるモードを利用者ごとに選べるようにした。慎重さを優先した画面は、慣れた人には遅く感じられるからである。誤りを止める機能は、このモードでも働く。
- **3工場で同じ画面**：画面と操作の順序を3工場で共通にした。工場をまたぐ応援者が、覚え直さずに作業できるようにするためである。

**設計プロセスの工夫**：私は、会議室で画面の図を見せても、現場で使えるかどうかは分からないと考えた。そこで**プロトタイプ**(試作品)を使って、仮説と検証を繰り返した。

| 段階 | やったこと | 分かったこと |
| --- | --- | --- |
| 1 紙の試作 | 紙に描いた画面を順にめくり、倉庫の責任者と操作の流れを確かめた | 棚を先に読むか部品を先に読むかで意見が分かれた。誤りを早く止められる「棚が先」に決めた |
| 2 実機の試作(1回目) | 動く試作品を倉庫に持ち込み、ベテランと応援者に実際の出庫をしてもらい、観察した | 手袋をした指では隣のボタンを押してしまう。棚の奥では画面の色が見えにくい |
| 3 実機の試作(2回目) | ボタンを大きくして間隔を空け、音と振動を加えて、もう一度試した | ベテランから「確認が多くて遅い」という声が出た。連続読取りのモードを追加した |

観察では、作業者に感想を聞くだけでなく、どこで手が止まったかを見た。作業者は、自分が迷ったことを覚えていないことが多いからである。確認が済んだ版を各工場の倉庫の責任者と合意して仕様を確定し、それ以降の変更要望は影響を評価してから採否を決めることにした。

**習熟を助ける仕組み**：紙の伝票から端末に変わると、作業の手順そのものが変わる。私は、画面ごとに次の操作を案内する表示に加え、本番の在庫に影響しない練習モードを組み込んだ。応援者が実際の棚と部品を使って練習できるようにするためである。エラーの表示は、「エラー番号」ではなく「この部品は検査待ちです。別のロットを取ってください」のように、次にすることを書いた。

### 場面8 夜間バッチ処理 ― 朝の業務に間に合わせ、エラーで止めない

**バッチ処理**とは、データをためておき、まとめて処理する方式である。新システムの夜間には、次の処理が順に動く。

1. 当日の実績を締め、在庫と発注残を確定する。
2. 3工場を通した所要量計算(**MRP**：生産計画と部品表から必要な部品の数と時期を計算し、在庫と発注残を差し引いて不足分の手配案を作る処理)を行う。
3. 翌日分の製造指示を作る。
4. 「出庫引当」を行う。**引当**とは、在庫を特定の生産のために確保することである。製造指示ごとに、どの棚のどのロットから出庫するかを決め、朝の出庫指示を作る。

私は2と4を設計した。★

**業務上の特性と制約**

- 資材部は始業と同時に、所要量計算の結果を見て発注と納期の督促を始める。
- 各工場の倉庫は始業と同時に出庫を始める。それまでに出庫指示ができていなければならない。
- 繁忙期には早出や残業があり、バッチ処理の最中にも入出庫が行われる。海外の営業拠点からの部品構成の照会は、時差のために日本の夜間に届く。
- 部品点数が多く、部品表の階層が深い。第1工場の計画から、第2・第3工場で作るユニットの必要数が決まり、そこからさらに部品の必要数が決まる。
- 部品は古いロットから先に使う(**先入れ先出し**)。長く置いた部品の劣化を防ぎ、設計変更の切替を確実にするためである。版が違う在庫があるときは、古い版を先に使う(場面6)。

**課題1：所要量計算の処理時間**

現行は、夜間に全品目を最初から計算し直していた。部品点数の増加で処理が延び、朝に間に合わない日が出ていた。私は次の2案を比較した。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A 全品目の再計算を速くする | 処理を品目のグループに分け、並行に動かす | 仕組みは現行に近い。しかし部品表の上位から下位へ順に計算する必要があり、分けられる範囲に限りがある |
| B 変化のあった品目だけを計算し直す | 前回の計算以降に、生産計画・部品表・在庫・発注に変化があった品目と、その下位の品目だけを計算する。**ネットチェンジ方式**という | 1日に変化する品目は全体の一部なので、処理が大きく減る。ただし「変化があった」ことを漏れなく記録する仕組みが要る |

私は案Bを選んだ。変化の記録は、在庫や計画を更新する処理が、更新のたびに「計算が必要な品目」の表に品目を書き込む形にした。業務処理をサーバ側の1か所にまとめてあるので、書き込みの漏れを防ぎやすい。場面5で3層にした効果である。

ただし、差分の計算を重ねると、万一の記録漏れが残り続ける恐れがある。そこで週末だけは全品目を計算し直し、平日の結果とのずれを解消することにした。

**課題2：出庫引当の処理時間**

出庫引当は工場の中で完結し、他の工場の在庫を取り合うことがない。そこで工場ごとに分けて並行に処理し、さらに工場の中をラインごとのグループに分けて並行に処理することにした。ただし、同じ工場の複数のラインが使う共通部品は、並行に引き当てると同じ在庫を取り合う。そこで共通部品だけは工場ごとに先に1本の流れで引き当て、その後でライン専用の部品を並行に処理する2段階の構成にした。さらに、朝一番に着手する製造指示から順に処理するようにした。万一遅れても、朝の作業は始められるからである。

**課題3：バッチ処理中の入出庫との競合**

全ての引当が終わるまで在庫をロックすると、早出の作業者が出庫できない。私は2つの工夫をした。第一に、製造指示1件を1つの**トランザクション**(全部成功か全部取消のどちらかになる、ひとまとまりの更新)とし、1件ごとに確定させてロックを短くした。第二に、引当では在庫数そのものは変えず、「引当済みの数」を別の項目として加算することにした。出庫できる数は、在庫数から引当済みの数を引いた数である。これで、入出庫と引当が同じ項目を取り合う場面が減る。

サーバの能力を増やす、夜間の入出庫を禁止する、といった対応も考えられた。しかし前者は繁忙期だけのために費用が掛かり、後者は現場の作業を縛る。私は、まず設計で解決すべきだと考えた。

**エラーがあっても続ける仕組み**

引当では、在庫の不足やマスタの登録漏れといったエラーが起こり得る。1件のエラーで全体を止めると、問題のない製造指示まで朝の出庫ができなくなる。そこで次の仕組みにした。

- エラーになった製造指示は、その1件分の更新だけを取り消して読み飛ばし、次の指示に進む。
- エラーの内容は一覧に記録する。朝、生産管理部の担当者が、どの指示が何の理由で止まったかを1つの画面で確認する。
- 製造指示ごとに「未処理・処理済み・エラー」の状態を持たせる。原因を直して再実行するときは、処理済みの指示を読み飛ばし、残りだけを処理する。

3つ目の理由は、再実行で同じ指示を2回引き当てると、在庫が二重に確保されて他の指示が欠品になるからである。何度実行しても結果が同じになる性質を**べき等性**という。

所要量計算の方は、品目1件のエラーを読み飛ばすと、その下位の品目の計算が全て誤る。そこで所要量計算では、エラーになった品目とその下位だけを「未計算」として残し、関係のない品目の計算は続ける設計にした。同じ「止めない」でも、処理の性質によって読み飛ばしてよい範囲が違う。

### 場面9 検査基準のマスタ化 ― 柔軟にする範囲を絞る

**背景**：受入検査や工程内検査の項目と合否の基準は、新機種の追加、設計変更、不具合の再発防止策などでたびたび変わる。現行システムでは基準がプログラムに埋め込まれており、変更のたびに改修が必要だった。改修が間に合わない間は、紙の記録で補っていた。紙で補った期間の記録はシステムに残らず、後の追跡の穴になっていた。

**柔軟性の対象にした業務ルール**

- どの品目の、どの工程で、何を検査するか。
- 合格とする値の範囲。
- 全数を検査するか、抜き取って検査するか。
- 不具合が出た仕入先の部品を、一定の期間だけ全数検査に切り替える運用。

**設計**：私は、検査の項目、規格値(上限と下限)、検査の方法(全数か抜取りか)を、品目と工程の組合せごとに**マスタ**(業務の基準となる、あまり変わらないデータ)として持たせた。マスタは3工場で共通である。検査の入力画面は、マスタの内容から項目を組み立てて表示する。これで、品質保証部の担当者が自分で基準を変えられる。

さらに、マスタの1件ごとに適用開始日と終了日を持たせた。理由は3つある。

- 設計変更の切替日より前に、新しい基準を登録しておける。
- 過去の検査記録を「当時の基準」で読み返せる。市場で不具合が起きたときの調査に欠かせない。
- 「一定の期間だけ全数検査にする」運用を、期間を区切った1件の登録で実現できる。期間が過ぎれば、自動で元の抜取りに戻る。戻し忘れが起きない。

マスタを利用部門が自由に変えられると、誤った登録がそのまま検査に使われる危険がある。そこで、登録した基準は別の担当者が承認するまで有効にならないようにした。

**絞り込み**：何でも変えられるようにすると、開発とテストの費用が膨らみ、設定の誤りも起きやすくなる。私は、現行システムに寄せられた過去の改修依頼を調べ、実際に変更が多かったものだけを柔軟にする対象にした。

| 区分 | 対象 | 理由 |
| --- | --- | --- |
| マスタで変えられる | 検査項目、規格値、全数か抜取りか、適用期間 | 過去の改修依頼の大半を占めていた |
| 固定とする | 合否を判定する方式(数値の上下限による判定と、良否の選択の2種類) | 計算式を自由に書ける仕組みは、設定の誤りが品質事故に直結する。誤りを確かめる手段を利用部門が持っていない |
| 固定とする | 不合格の後の流れ(保留の在庫に移す) | 過去に変更がなく、在庫の状態管理と強く結び付いている |
| 固定とする | 検査成績の帳票の様式 | 顧客に提出する様式は種類が限られ、変更はまれである |

この絞り込みが適切だと考えた理由は2つある。過去の変更の実績という事実に基づいていること。そして、固定にした部分はプログラムを1か所にまとめてあり、将来必要になればそこだけを改修すれば済むことである。稼働後、検査基準の変更で改修の依頼は出ていない。

### 場面10 仕入先ポータル ― 会えない利用者の画面を決める

第2期に、仕入先がインターネット経由で注文を確認し、納期を回答し、現品票を印刷する「仕入先ポータル」を開発した。それまではファクシミリと電子メールでやり取りし、資材部が回答を手で入力していた。入力の遅れと誤りが、所要量計算の精度を下げていた。

**利用者と接点がない**：利用者は多数の別会社の担当者である。私が1社ずつ訪ねて要望を聞くことはできず、会社の規模もコンピュータへの慣れも様々である。操作の研修に集まってもらうこともできない。

**利用者像の想定**：私は、日頃仕入先とやり取りしている資材部の担当者に話を聞き、現在の納期回答のやり方を仕入先ごとに分類した。分類の軸は、注文の件数の多さと、回答の手段(電子メールにファイルを添付するか、ファクシミリに手書きするか)である。その結果から、典型的な利用者を具体的な人物像として描いた**ペルソナ**を2つ作った。

| 人物像 | 特徴 | 求めるもの |
| --- | --- | --- |
| 大手の仕入先の営業事務担当 | 毎日PCで多くの注文を処理する。自社の受注システムを持つ | まとめて回答したい。自社のデータを取り込みたい |
| 小規模な加工業者の経営者 | 現場の仕事の合間に操作する。PCには不慣れで、注文の件数は少ない | 迷わず終わらせたい。説明書は読まない |

**提供する機能**：注文の確認、納期の回答(指定どおり、遅れる、分けて納める)、現品票の印刷、検査成績書の提出である。

**課題と対応**：2つの人物像は求めるものが逆である。私は次の2案を比較した。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A 画面を2系統用意する | 利用者が自分に合う方を選ぶ | それぞれに最適だが、開発と保守が2倍になる。どちらを選ぶかで迷う |
| B 簡素な画面を入口にして、そこから高度な操作に進める | ログイン直後は「回答が必要な注文」だけを表示する。指定どおりの納期ならボタン1つで回答できる。複数選択やファイルでの一括回答は、その画面から進める | 不慣れな人は迷わず、慣れた人も1回の操作で一括処理に進める |

私は案Bを選んだ。小規模な仕入先が使えなければファクシミリが残り、資材部の手入力がなくならず、開発の目的を達成できないからである。判断の裏付けとして、資材部を通じて規模の異なる数社に試作品を見てもらった。

もう1つの課題は、操作の案内をどこまで付けるかである。案内が多いと慣れた人には邪魔になり、少ないと不慣れな人が止まる。私は、初めての操作のときだけ案内を表示し、利用者が消せるようにした。

注文の一覧と現品票には、納入先の工場を大きく表示した。3工場のどこに納めるかを間違えると、受入で止まるからである。

**継続的に改善する工夫**：稼働前に全ての利用者の反応を確かめることはできない。私は、稼働後に改善点を見つけて直し続けられるように、次の3つを設計に組み込んだ。

- 画面ごとの利用状況を記録する機能。どの画面で操作をやめたか、どこでエラーになったか、期限までに回答されなかった注文はどれかを集計できる。
- 資材部に届いた問合せを、画面と内容で分類して記録する運用。
- 画面を独立した部品に分け、テストを自動化して、小さな改訂を短い間隔で出せる構造。

稼働後、利用状況の記録から、現品票の印刷の画面で操作をやめる利用者が多いことが分かった。問合せの記録と照らすと、原因は印刷の設定の分かりにくさだった。そこで印刷の手順の案内を画面に追加した。利用状況の記録だけでは「どこで」しか分からず、問合せの記録だけでは「どれだけ多いか」が分からない。2つを組み合わせたことで、直すべき点を絞れた。

**セキュリティ**：社外に公開するので、次の対策を取った。

- パスワードに加えてもう1つの手段で本人を確かめる**多要素認証**。
- 仕入先が自社の注文だけを見られるようにする**アクセス制御**。
- 誰がいつ何をしたかを残す操作記録。
- 仕入先ポータルのサーバを、社外から接続できる区画に分けて置き、社内のデータベースには決められた処理を通してだけ到達できるようにする。

## 物語 第3部：テスト、移行、稼働後

### 場面11 システムテストの計画 ― 人が見るべき所だけを人が見る

**システム適格性確認テスト**(システムテスト)は、機能要件と非機能要件を満たしているか、実際の業務として運用できるかを確かめるテストである。プログラム単体やプログラム間のつながりを確かめるテストとは違い、業務の流れを最初から最後まで通す。

**テストの区分け**：私はテストを次の3つの軸で区分けした。

| 軸 | 区分 | そう分けた理由 |
| --- | --- | --- |
| 業務の周期 | 日次(受入から出庫、実績、夜間バッチ処理)、月次(在庫金額の会計連携)、期末(棚卸) | 周期ごとに前提データと日付が違う。日次を先に固め、その結果のデータを月次と期末に引き継げば、準備の重複がなくなる |
| 製品の種類 | 標準機、特注機 | 部品の引当方法が違い、通る処理が異なる |
| 工場の範囲 | 1つの工場の中で完結する流れ、工場をまたぐ流れ(第2・第3工場での製造、送り出し、輸送中、第1工場での受け取りと組込み) | 工場の中の流れを先に3工場で並行して確かめ、その後で工場をまたぐ流れを通す。問題が出たときに、原因がどの工場のどの処理にあるかを切り分けやすい |
| 状況 | 通常、例外(検査不合格、設計変更の切替、回線が切れたときの一時保存、紙の代替運用からの復帰) | 例外は準備に手間が掛かるので、まとめて実施する方が効率がよい |

**実施上の配慮**

- **テストデータ**：移行のリハーサルで作った本番相当のデータを使う。テスト用にデータを作る手間が省け、移行結果の検証も兼ねられる。
- **業務日付の切替**：コンピュータの日付とは別に「業務上の日付」を持たせ、テスト中に月末や期末を再現できるようにした。実際の月末を待たずに済む。
- **利用部門の参加**：3工場の倉庫と製造の責任者に、自分の工場で実際の端末を操作してもらう。繁忙期を避けて日程を組んだ。

**結果の確認方法**：所要量計算の結果や在庫金額は件数が多く、目で確かめることはできない。私は2つの方法を採用した。

1つ目は**現新比較**である。現行システムと新システムに同じ入力を与え、結果をツールで突き合わせて、差異だけを取り出す。ただし、新システムは仕様を変えた部分があるので、差異が出て当然の箇所がある。差異を全て人が調べると、かえって手間が増える。そこで「仕様変更によって生じるはずの差異」を事前に一覧にし、ツールが想定内と想定外に仕分けるようにした。人が調べるのは想定外の差異だけである。

現新比較で想定内とした差異の例は次のとおりである。

| 差異が出る箇所 | 理由 |
| --- | --- |
| 設計変更の前後の部品の必要数 | 新システムは使い切りで切り替えるので、切替の時期が現行と違う |
| 検査待ちの部品を含む品目の不足数 | 新システムは検査待ちを使える在庫に数えない |
| 第1工場のユニットの在庫 | 新システムは輸送中の数を別に持つ |

2つ目は整合性の機械的な検査である。ハンディ端末の操作は現行に比較対象がない。そこで、受払履歴の合計と在庫の残高が一致するかを検査する処理を用意し、テストの区切りごとに実行した。この処理は、稼働後も日々の点検に使っている。

**非機能要件の確認**：性能は、業務の集中を再現して確かめた。3工場の始業直後の出庫を想定し、見積もった数の端末から同時に読取りを行って、場面4で決めた「次の部品に手を伸ばすまでに結果が出る」を満たすかを見た。可用性は、片方のサーバを実際に止め、出庫が続けられることと、止めた瞬間の読取りが失われないことを確かめた。専用線を抜いて予備回線に切り替わること、端末の一時保存が後で送信されることも、第2工場で実際に試した。

**振り返り**：想定内の差異の一覧は、作るのに手間が掛かった。しかし、この一覧を利用部門と一緒に作ったことで、「新システムは現行と何が違うか」を利用部門が稼働前に理解できた。テストの効率だけでなく、稼働後の混乱を減らす効果もあった。

### 場面12 データ移行 ― 現行に無い情報は、業務で作る

**(1) 現行と新システムの差異と、移行の方法**

★ 私はまず、現行データの項目の意味と、実際に入っている値の種類を調べた。現行の項目と新システムの項目を対応づける作業を**データマッピング**、誤り・重複・表記の揺れを正す作業を**データクレンジング**という。調査で分かった主な差異と対応は次のとおりである。

| 差異 | システム面の対応 | 業務面の対応 |
| --- | --- | --- |
| **品目コード**：現行は同じ部品に複数のコードが登録されている。新システムは1部品1コード | 図面番号とメーカーの型番が一致するものを、同じ部品の候補として抽出する。確定した対応を新旧の対応表にして変換する | 候補が本当に同じ部品かは、資材部と設計部が確認して決める。このように同じものを指すデータを1つにまとめることを**名寄せ**という |
| **在庫の細かさ**：現行は工場と倉庫ごとの合計だけ。新システムは棚番・ロット別 | 現行の残高は移行せず、棚卸結果との突き合わせにだけ使う | 移行直前の期末棚卸で、新システムのハンディ端末を使って棚番・ロット別に現品を数え、その結果を初期在庫にする |
| **棚の呼び方**：現行は工場ごとに付け方が違う。新システムは3工場で共通の棚番体系 | 新しい棚番のマスタを作り、棚に2次元コードを貼る | 各工場の倉庫の責任者が、現在の棚と新しい棚番の対応を決める |
| **数量の単位**：現行は一部の部品を箱単位で管理。新システムは個単位 | 品目ごとの換算数を登録し、一括で変換する | 換算で端数が出る品目は一覧にし、担当者が確認する |
| **版**：現行は内製品の版を在庫に持たない。新システムは版ごとに在庫を持つ | 版のマスタを事前に登録する。現行のデータから版を推定して埋めることはしない | 期末棚卸で、現品票のコードから版を読み取って登録する。版の表示が無い古い現品は「版不明」として登録し、先に使い切る |
| **仕掛品**：現行は品目が無い。新システムは中間品として管理する | 中間品の品目と製造部品表を事前に登録する | 期末棚卸で、棚にある仕掛品に現品票を付けて数える |
| **過去の履歴**：受払や検査の記録の構造が異なる | 移行しない。現行システムを参照専用で残す | 過去の記録が必要なときは現行システムで調べる |

最も悩んだのは在庫の細かさである。現行データには棚番もロットも無いので、どれだけ変換を工夫しても作り出せない。私は、システムで解決できない差異は業務で埋めるしかないと判断した。期末にはもともと3工場で一斉に全部品を数える棚卸がある。その棚卸を新システムの端末で行えば、追加の作業をほとんど増やさずに、棚番別の正確な初期在庫が得られる。作業者が端末に慣れる機会にもなる。

**データの品質を上げる手順**：名寄せや棚番の対応づけは、1回では終わらない。私は「抽出する、確認してもらう、直す、もう一度流す」を繰り返す前提で、変換の処理を何度でも最初からやり直せるように作った。変換でエラーになった行は理由を付けて一覧に出し、担当部門が直す先(現行のデータを直すか、対応表を直すか)を決める。リハーサルのたびにエラーの件数が減っていくことを、移行の準備が進んでいる目安にした。

**(2) 移行方式の選択**

移行方式には、ある日を境に全てを切り替える**一斉移行**、拠点や機能ごとに順に切り替える**段階移行**、新旧を同時に動かして結果を比べる**並行運用**がある。B社は3工場あるので、私は次の3案を比較した。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A 3工場の一斉移行 | 期末の連休に3工場を同時に切り替える | 所要量計算と工場間の移動が、常に1つのシステムで一貫する | 失敗したときの影響が3工場に及ぶ。稼働直後の支援の要員が3工場に分散する |
| B 工場ごとの段階移行 | 規模の小さい工場から順に切り替える | 影響の範囲が小さい。先の工場で得た経験を次の工場に活かせる | 切替の途中は、新旧のシステムにまたがって部品が行き来する |
| C 並行運用 | 新旧の両方に記録し、結果を比べてから切り替える | 結果を確かめてから切り替えられる | 現場が二重に記録することになる |

私は、業務の特性から来る制約を整理した。

- 3工場は1つの製品を分担して作る。第2・第3工場の制御装置と関節ユニットは、毎日第1工場に送られる。案Bでは、送り出す工場と受け取る工場が新旧に分かれる期間ができ、その間、輸送中の在庫を新旧の両方で二重に管理しなければならない。
- 所要量計算は3工場を通して行う。案Bでは、切替の途中の期間、全社で一貫した計算ができない。
- 現場には、新旧の2つの方法で二重に記録する余力がない。
- 3工場を同時に止められるのは、期末棚卸のある長期の連休だけである。

案Bは一般には安全な方式だが、B社では工場間の結び付きが強く、新旧をまたぐ期間の方がかえって危険だと判断した。案Cは3つ目の制約から採れない。私は案Aを選び、期末の連休に3工場を一斉に移行することにした。

その上で、案Aの短所を次のように補った。在庫に直接関わらない仕入先ポータルと品質情報提供を第2期に分け、一度に切り替える範囲を小さくした。また、連休の前に第3工場で、新システムの端末を使った棚卸の予行を行った。最も規模の小さい工場で手順と所要時間を確かめ、3工場の本番の手順書に反映するためである。

**(3) 移行のタイミングと実施方法**

検討の観点は、連休中に終わるか(作業時間)と、誤りなく移せるか(作業品質)である。

- **マスタは事前に移行する**：品目や部品表は件数が多く、名寄せの確認に日数が掛かる。連休前に移行を済ませ、その後の変更だけを差分として蓄積し、移行日に反映する。差分を確実につかむため、事前移行の後は現行システムのマスタ変更を申請制にした。
- **残高は移行日に一括で移行する**：在庫と発注残は、切替直前の値でなければ意味がない。
- **リハーサルを行う**：本番と同じ手順を事前に繰り返して所要時間を測り、手順書を直す。
- **移行結果を検証する**：件数と金額の合計を新旧で照合し、重要部品は現品と照らし合わせる。
- **切り戻しを準備する**：連休の途中に判定の時点を設け、基準を満たさなければ現行システムに戻す。基準と判定者は事前にB社と合意した。

連休中の作業の順序は次のとおりである。

1. 現行システムの入力を締め、最終のデータを取り出す。
2. マスタの差分を反映する。
3. 3工場で、新システムの端末を使って棚卸を行う。
4. 棚卸の結果を初期在庫として取り込み、現行の残高と突き合わせる。差の大きい品目は数え直す。
5. 発注残と仕掛中の製造指示を移行する。
6. 件数と金額を検証し、切り替えるか戻すかを判定する。
7. 所要量計算を1回実行し、結果を生産管理部と確認する。

**(4) 移行後の業務に支障を出さない工夫**

| 想定した支障 | 工夫 |
| --- | --- |
| 稼働直後、作業者が端末の操作に手間取り、出庫が滞る | 稼働直後は生産量を抑えた計画にするよう生産管理部と調整した。3工場同時の稼働ではA社の要員が分散するので、各工場の職場ごとに操作を教えられる担当者を事前に育てた。A社の要員は各工場に待機し、3工場で起きた問題を毎日持ち寄って共有した |
| 工場間で送った品物が、輸送中のまま受け取られずに残る | 輸送中の在庫を一覧で見られる画面を用意し、送り出しから日数がたったものを生産管理部が毎日確認した |
| 棚番の登録誤りで部品が見つからない | 稼働後しばらくは、重要部品を対象に**循環棚卸**(全体を止めずに、一部ずつ順に数える棚卸)を行い、誤りを早く見つける |
| 所要量計算の結果が従来の感覚と違い、発注の担当者が判断に迷う | 最初の期間は、計算結果を生産管理部と私が一緒に確認し、従来との違いとその理由を説明した |

### 場面13 稼働後の評価と残った課題

評価は、場面1で挙げた4つの問題と同じ物差しで行った。

- **各工場の倉庫**：応援者がベテランに尋ねずに出庫できるようになった。棚番と画面を3工場でそろえたので、他の工場から来た応援者もすぐに作業できると、各工場の製造課から評価された。
- **生産管理部**：期末棚卸の差異が大きく減った。担当者は、手元の表計算ソフトで余裕を上乗せする作業をやめた。他の工場の在庫を電話で確かめることもなくなり、ある工場で不足した部品を別の工場の在庫から融通できるようになった。
- **第1工場の組立**：制御装置と関節ユニットが輸送中か到着済みかを画面で確かめられ、組立の段取りを前もって決められるようになった。
- **品質保証部**：不具合ロットを組み込んだロボットの特定が、3工場の紙の記録をめくる作業から、画面での検索に変わった。

一方で、次の課題が残った。

- ロットを記録するのは重要部品だけである。対象を広げるには組立作業者の読取りの負担が増える。仕入先が現品票に2次元コードを印字する範囲が広がれば負担が減るので、それに合わせて段階的に広げる。
- 組立日程の自動作成は未着手である。実績から標準時間のデータを蓄積している段階である。
- 回線が切れたときの一時保存は出庫だけが対象で、受入検査は紙の代替運用になる。

試験で評価を書くときは、「課題と同じ物差しでの結果」「利用部門からの評価」「残った課題と今後の対応」の3点をこの順で書く。

### 場面14 品質指標の提供 ― 2つのシステムのデータをつなぐ

第2期に、品質保証部と設計部に向けて品質の指標を提供する機能を追加した。

**業務目標とニーズ**：品質保証部の業務目標は、出荷後の故障を減らし、故障の兆しを早くつかむことである。最初に聞いた要望は「どの部品が悪いのか分かるようにしてほしい」という漠然としたものだった。私は、誰が何の判断に使うのかを尋ねて要望を具体化した。品質保証部は、仕入先に改善を求めるか、受入検査を厳しくするかの判断に使う。設計部は、部品の選び直しの判断に使う。どちらも「部品のロット」と「仕入先」の単位で見たいことが分かった。

**提供した指標**：部品ロット別の故障発生率である。あるロットの部品を組み込んで出荷したロボットのうち、その部品の交換修理が発生した台数の割合を表す。目標の達成度を測るための数値を**KPI**(重要業績評価指標)という。

**収集したデータ**

| 収集元 | データ | 使い道 |
| --- | --- | --- |
| 生産・在庫管理システム(現場系) | シリアル別の部品構成(どのロボットにどのロットを組み込んだか)、受入検査の結果 | 分母の台数、ロットと仕入先の特定 |
| 保守サービスシステム | 国内と海外の営業拠点が入力した修理履歴(シリアル、交換した部品、故障の現象、修理日) | 分子の台数 |
| 販売管理システム | 出荷日、納入先 | 稼働期間の計算 |

**設計で検討したこと**

- **算出の手順**：分母を単純に出荷台数とすると、出荷したばかりのロボットは故障していなくて当然なので、新しいロットほど良く見えてしまう。そこで出荷後の経過期間で区切り、同じ経過期間どうしで比べることにした。
- **データ定義の差の吸収**：部品のコードは、場面6の変換表で品目コードにそろえる。故障の分類は、保守側の現象の分類を品質保証部の分類に対応づける表を作った。
- **収集の方式**：夜間に各システムからデータを取り出し、形式をそろえて分析用のデータベースに書き込む。この一連の処理を**ETL**という。業務用のデータベースで直接集計しないのは、集計の負荷で現場の端末の応答が遅くなることを避けるためである。
- **版ごとの集計**：同じ部品でも、版ごとに発生率を出せるようにした。4M変更の前後で故障の出方が変わったかを確かめるためである(場面6)。
- **見せ方**：ロットの一覧で、発生率が高いものを強調する。ロットを選ぶと、そのロットを組み込んだロボットの一覧にたどれる。

**データの内容の問題と対応**

| 問題 | 対応 |
| --- | --- |
| 保守サービスシステムの修理履歴では、交換した部品が自由な文章で書かれ、シリアルの入力漏れもあった | 新しいデータ取得の仕組みを作った。保守員が修理のときに、交換した部品の現品票とロボット本体の銘板の2次元コードを読み取って入力する方法に変えた。過去の分は、品質保証部が重要部品に絞って整備した |
| 海外の営業拠点の修理履歴は現地の言葉で書かれ、故障の分類の選び方も拠点ごとに違っていた | 故障の現象を選択式の共通の分類にそろえ、文章は補足の扱いにした。分類の選び方の手引きを作り、品質保証部が国内と海外の拠点に展開した。過去の分は、交換した部品のコードだけを使い、現象の分類は集計の対象から外した |
| 現行システムの時代に製造したロボットは、部品のロットが紙にしか残っていない | みなし処理を行った。組立日と当時の入出庫の記録から、その時期に使われていたロットを推定した。推定したロットは画面で「推定」と表示し、確定した記録と区別した |
| 台数の少ないロットは、1台の故障で発生率が大きく振れる | 率だけでなく台数を並べて表示し、台数の少ないロットには注記を付けた |

みなし処理で区別の表示を付けたのは、推定を事実と誤解して仕入先に改善を求めると、B社の信用に関わるからである。推定のロットで判断するときは、紙の組立記録で確かめる運用とした。

### 場面15 検査成績書の読取りへのAIの適用 ― 小さく試してから決める

**業務の内容**：仕入先は、納める部品に検査成績書(寸法や特性の測定値を記した書類)を添付する。各工場に配置された品質保証部の検査員は、受入検査の一部として、成績書の値を図面の規格値と1項目ずつ照合し、合否と値をシステムに入力していた。

**人手でしかできないと考えられていた理由**

- 仕入先ごとに様式が違い、同じ仕入先でも部品によって違う。
- 従来の文字読取りの技術は、様式ごとに「どの位置に何が書いてあるか」を定義する必要がある。様式の種類が多く、定義の費用が効果に見合わない。
- 手書きの値や押印が混ざる。
- 読み違いが品質事故につながるので、人の目が欠かせないと考えられていた。

**適用した技術**：**AI-OCR**(機械学習を使い、様式を事前に定義しなくても文字と表の構造を読み取る技術)のソフトウェア製品である。

**適用の方法**

1. 成績書を取り込む(紙はスキャンし、電子ファイルはそのまま)。
2. AI-OCRが項目名と測定値を取り出す。
3. 場面9の検査基準マスタの規格値と自動で照合する。
4. 検査員の画面に、照合の結果と元の成績書の該当箇所を並べて表示する。
5. 検査員が確認して確定する。

**大幅な効率化が可能と考えた理由**：作業を観察すると、時間の大半は値を読むことではなく、規格値との照合と入力に使われていた。照合と入力は、規格値がマスタにあれば機械的に行える。AIが苦手な部分だけを人に回せば、全体として成り立つと考えた。

**概念実証**：新しい技術を本格的に導入する前に、小さく試して、実現できるかと効果があるかを確かめることを**PoC**(概念実証)という。私は次の仮説を立てた。「印字された成績書であれば、検査員の確認を前提に、実用になる精度で読み取れる。その結果、照合の時間を減らせる」。

- **検証の方法**：過去の成績書には、検査員が入力した結果が残っている。AIの読取り結果をこの記録と突き合わせて、正しく読めた割合を調べた。成績書は「印字か手書きか」「表の複雑さ」で分類し、分類ごとに評価した。時間については、検査員に従来の方法と新しい方法の両方で作業してもらって比べた。
- **工夫1**：経験の長い検査員に参加してもらい、読み違いを「危険な読み違い」(規格外の値を規格内と読む)と「安全側の読み違い」に分けて評価した。全体の正しさの割合だけでは、業務に使えるかを判断できないからである。
- **工夫2**：AIが読取りに自信を持てなかった項目に色を付ける表示を、試作に含めた。
- **工夫3**：規格値の桁から大きく外れる値を警告するようにした。小数点の読み落としを見つけるためである。

**検証の結果と適用の判断**：印字された成績書はほぼ正しく読め、照合の時間が大きく減った。危険な読み違いは少数あったが、色付きの表示と桁の警告によって、検査員が全てに気付けた。一方、手書きが中心の成績書は読み違いが多く、確認の手間で効果が打ち消された。

私は次のように判断した。印字された成績書を出す仕入先に限って適用する。合否を確定するのは必ず検査員とし、自動では確定しない。手書きの仕入先には、仕入先ポータルから測定値をデータで提出してもらう方法を案内する。

**適用で生じた課題と対策**

| 課題 | 対策 |
| --- | --- |
| 読み違いによる誤った合格 | 最終の判定は検査員が行う。元の成績書を並べて表示する |
| 検査員がAIの結果を信用しすぎて、確認が形だけになる | AIが自信を持てなかった項目は、検査員が1項目ずつ確認の操作をしないと確定できないようにした |
| 仕入先が成績書の様式を変えると、読取りの正しさが下がる | 検査員が直した項目を記録し、仕入先ごとの直しの多さを品質保証部が毎月確認する。直しが増えた仕入先は、様式の変更がないかを資材部から確かめる |

### 場面16 稼働後の機能追加と、一部でのアジャイル開発

**(1) 補修部品の即納サービスに伴う機能追加**

**背景と業務要件**：稼働後、B社は保守契約を結んだ顧客に向けて、補修部品を即日出荷するサービスを始めることにした。補修部品の要求は、国内5都市と海外2か国の営業拠点から、保守サービスシステムを通じて届く。業務要件は「契約した顧客の修理に必要な主要な補修部品を、営業拠点が要求した当日に工場から出荷できること」である。

**業務の課題**：補修部品は、生産用の部品と同じ在庫から出していた。そのため、生産用に引き当てられて修理のときに在庫が無い、逆に補修用に出されて生産が欠品する、という問題が両方起きていた。

**業務要件の分析**：私は3つの視点で分析した。

- **契約条件の視点**：どの部品を、どの顧客に、いつまでに届ける約束か。対象は主要な補修部品に限られることが分かった。
- **業務プロセスの視点**：誰が要求し、誰が出庫し、どこから出荷するか。要求するのは国内と海外の営業拠点、出荷するのは製品の出荷拠点でもある第1工場である。出庫と出荷は既存の倉庫の作業と同じでよいことが分かった。海外向けは輸送に日数が掛かるが、約束の内容は「当日の出荷」であり、工場の作業は国内向けと変わらないことも確かめた。
- **関連するシステムの機能の視点**：引当、所要量計算、保守サービスシステムとの連携のどこに影響するか。

分析の結果、必要なのは「補修用に確保した数を、生産用の引当から守ること」であると分かった。倉庫や棚を物理的に分ける必要はない。

**設計**：私は2案を比較した。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A 補修用の倉庫を別に設ける | 補修用の在庫を別の場所に移して管理する | 分かりやすいが、在庫を二重に持つことになり総量が増える。移し替えの作業が増え、先入れ先出しも崩れる |
| B 同じ在庫の中に「補修用の確保数」を設定する | 第1工場の在庫に、品目ごとの確保数を登録する。生産用の引当は、在庫数から確保数を引いた範囲で行う | 在庫は増えず、現場の作業も変わらない |

私は案Bを選んだ。確保数は、所要量計算には**安全在庫**(欠品を防ぐために常に持っておく余裕の在庫)として渡す。こうすると、確保数を割り込んだときに、既存の所要量計算がそのまま補充の手配案を作る。所要量計算の処理には手を入れずに済む。

**既存への影響を小さくする工夫**

- 引当の処理そのものは変えず、「引当できる数」を求める共通の処理1か所だけを変えた。用途の区分を追加したが、既定の値を「生産用」にしたので、既存のデータと画面は従来どおり動く。
- 確保数のマスタに適用開始日を持たせ、サービス開始日より前に登録とテストを済ませた。
- 保守サービスシステムとの連携は、既存のAPIに省略可能な項目を追加する形にした。相手側の改修の時期に左右されない。
- 影響の範囲は、**CRUD図**(どの機能がどのデータを作成・参照・更新・削除するかをまとめた表)で特定した。その範囲で**回帰テスト**(変更していない部分が壊れていないことを確かめるテスト)を行った。

**(2) 組立ラインのタブレット画面でのアジャイル開発**

★ この部分は実際の経験と重なる。体制、会議の進め方、役割の兼務で困ったことは、自分の現場の事実で置き換えて書ける。

**アジャイル開発を選んだ理由**：第1期の大部分は、工程を順に進める**ウォーターフォール型**で開発した。他システムとの連携と移行日が決まっており、在庫を更新する中核の処理は要件を先に固める必要があったからである。

ただし、組立ラインのタブレット画面(作業の実績と部品ロットの記録)だけは、**アジャイル開発**(短い期間で動くものを作り、利用者の反応を見て直すことを繰り返す進め方)を選んだ。理由は3つある。

- 作業者の使いやすさが要件を左右し、使ってみないと決めきれない。
- 利用部門が、欲しいものを文書で説明することに慣れていない。動くものを見せた方が早い。
- 在庫を更新する処理は既にサーバ側にまとまっており、画面はその上に載るだけなので、後から直しても中核に影響しない。

**体制**：手法は**スクラム**を用いた。開発者は私を含めて3名、プロジェクトマネージャが1名、利用部門から製造課の責任者と品質保証部の担当者の2名が参加した。

| 役割 | 本来の役目 | このチームでの担当 |
| --- | --- | --- |
| **プロダクトオーナ** | 何を作るかと、その優先順位を決める | 利用部門の2名。ただし当初は私が作業の多くを代行した |
| **スクラムマスタ** | スクラムの進め方を支え、妨げを取り除く | 私 |
| 開発者 | 動くものを作る | 私を含む3名 |

**進め方**：**スプリント**と呼ぶ短い期間を繰り返した。各スプリントで次の会議を行った。

| 会議 | 内容 |
| --- | --- |
| スプリントプランニング | スプリントの最初に、今回作るものを**プロダクトバックログ**(作りたいものを優先順に並べた一覧)から選ぶ |
| デイリースクラム | 毎日短い時間で、開発者が進み具合と困りごとを共有する |
| プロダクトバックログリファインメント | 次回以降に作るものの内容を詰め、大きさを見積もり、順番を見直す |
| スプリントレビュー | スプリントの最後に、動くものを利用部門に見せて意見をもらう |
| スプリントレトロスペクティブ | チームの進め方を振り返り、次のスプリントで変えることを決める |

**ユーザストーリ**：要件は**ユーザストーリ**(誰が・何のために・何をするか)で表した。

- 組立作業者が、部品の取り違えを防ぐために、組み込む部品の現品票を読んで照合する。
- 組立作業者が、作業の漏れを防ぐために、自分の工程で残っている作業を確認する。
- 検査員が、記録の転記をなくすために、工程内検査の結果をその場で入力する。
- 班長が、遅れに早く気付くために、ラインの進み具合を一覧で見る。

**分類と大きさの調整**：ユーザストーリを「誰が」(組立作業者、検査員、班長)と「どの工程で」で分類した。この分類にした理由は、利用者と工程によって端末の使い方と必要な情報が違うからである。分類して並べると、検査員のストーリが1件も無い工程があることに気付き、不足分を追加できた。

大きさは、開発者3名で相対的に見積もった。1スプリントに収まらないものは、操作の切れ目で分けた。例えば部品の照合は、「現品票を読んで品目を照合する」「ロットを記録する」「誤った部品を読んだときに止めて班長に知らせる」の3つに分割した。逆に、表示の文言の修正のような小さなものは、1つにまとめた。

**優先順位**：「誰が」にとっての価値に着目した。最も重く見たのは、誤った部品の組付けを防ぐという価値である。品質問題に直結し、作業者自身の手戻りも減るからである。そのため部品の照合を最優先とし、班長向けの一覧は後のスプリントに回した。班長の一覧は、作業者の記録がたまって初めて意味を持つ、という順序の理由もあった。

**課題：プロダクトオーナの役割が回らない**

利用部門の2名は、アジャイル開発が初めてだった。優先順位を尋ねても「全部必要」という答えになり、ユーザストーリを書くこともできなかった。そこで当初は、私がストーリを書き、優先順位の案も作った。つまり私は、スクラムマスタ、開発者、プロダクトオーナの代行の3つを兼ねていた。

私はこの状態に2つの危険があると考えた。第一に、作る側が優先順位を決めると、作りやすいものが先になり、利用者にとっての価値の順にならない。第二に、利用部門が「自分たちが決めたもの」と感じられず、出来上がったものへの責任が開発側に寄ってしまう。

**対応**：私は、代行する範囲を「案を作るところまで」に限り、決めるのは必ず利用部門の2名とした。

- 優先順位は、私が案と判断の材料(そのストーリが無いと現場で何が困るか、作るのにどれだけ掛かるか)を出し、リファインメントで2名が決める。「全部必要」とならないよう、「次のスプリントに入るのはこのうち3件です。どれにしますか」と、選ぶ形で尋ねた。
- ユーザストーリは私が下書きし、2名に「誰が」と「何のために」が現場の実態と合っているかを直してもらう。
- スプリントレビューは会議室ではなく組立ラインで行い、作業者に実際に触ってもらう。その場で出た意見を、2名が次の優先順位に反映する。
- スプリントを重ねるごとに、2名の担当を広げる。まず「完成と認める条件」を2名に書いてもらうことから始めた。

レトロスペクティブでは、開発者から「私に作業が集中し、デイリースクラムが私への報告の場になっている」という指摘が出た。これを受けて、デイリースクラムの進行を開発者の持ち回りにした。

**結果と残った課題**：スプリントレビューを現場で行うようになってから、2名が自分の言葉で優先順位を説明するようになった。作業者から出た「手袋のまま読取りのボタンを押したい」という意見は、2名の判断で次のスプリントの最優先になった。一方、私の兼務は解消していない。プロダクトオーナの役割を利用部門に完全に移すことと、スクラムマスタを開発者の1人に引き継ぐことが、残った課題である。

### 版と仕掛品の話を使える問題

場面6の(3)と(4)は実際の経験に近いので、具体的に書きやすい。次のテーマで、主役または補強の材料として使える。

| テーマ | 使い方 |

| 機能追加における業務要件の分析(2021 問2)、業務機能の変更・追加(2015 問2) | 「版が違えば別の物として扱いたい」という要望を、部門ごとの見方の違いとして分析し、3案から選ぶ |

合わない問題が来たときは、次の順で考える。問題文が挙げている例に最も近い場面を1つ選ぶ。その場面の「課題・案の比較・選んだ理由」を、設問の言葉に合わせて言い換える。物語に無い事実を増やすのは、設問が直接求めている部分だけにとどめる。

## 設問ア用の持ち駒

設問アは800字以内である。次の4つの段落を覚えておき、問題に合わせて組み合わせる。設問アが求める項目は毎回違うので、求められた項目を見出しにして、対応する段落を置く。

**段落A：対象の業務**

> B社は、工場の溶接や搬送に使われる産業用ロボットを製造・販売する、社員約1,000名の機械メーカーである。国内に3つの工場を持ち、制御装置と関節ユニットを2つの工場で作り、本社工場で本体に組み立てて出荷する。営業拠点は国内5都市と、アメリカ、中国にある。標準機に加えて顧客ごとに仕様を変える特注機も多く、製品は1台ごとにシリアル番号で管理する。対象の業務は、3工場を通した生産計画、部品の所要量計算と発注、受入と検査、倉庫での保管と出庫、工場間の移動、組立、出荷までの生産管理業務と在庫管理業務である。部品点数が多く構成の階層が深いこと、重要部品をロット単位で追跡する必要があること、3工場が1つの製品を分担して作ることが、業務の特徴である。

**段落B：情報システムの概要**

> 対象の情報システムは、B社の生産・在庫管理システムである。生産計画、所要量計算、発注を行う計画系と、受入、検査記録、入出庫、組立実績を記録する現場系から成る。画面、業務処理、データベースの3層で構成するWebシステムで、サーバは本社工場に置き、第2・第3工場は専用線を通って利用する。事務所はPC、倉庫はハンディ端末、製造ラインはタブレットで利用する。販売管理、設計部品表管理、保守サービス、会計の各システムと連携する。

**段落C：再構築の背景**

> 従来のシステムは、在庫を工場と倉庫ごとの合計でしか持たず、入出庫の実績を翌日にまとめて入力していた。棚の呼び方や伝票の書き方も工場ごとに違っていた。そのため帳簿と現品が合わず、所要量計算の結果が信用されない、他の工場の在庫や輸送中の品物が分からない、不具合のあった部品を組み込んだ製品の特定に手間が掛かる、という問題があった。B社はシステムの保守期限を機に、現品が動いたその場で記録し、その記録を3工場で同じ形で持つことを基本方針として再構築を決めた。

**段落D：私の立場**

> 私は、ソフトウェア開発会社A社のシステムアーキテクトとして、このシステムの要件定義、システム方式設計、外部設計、システムテスト計画、移行設計を担当した。

### 組み合わせ方の例

| 設問アが求めるもの | 置く段落 | 足す内容 |
| --- | --- | --- |
| 対象業務と情報システムの概要(2019問2、2017問1など) | A、B、D | 設問イにつながる特徴を1文。例：倉庫の出庫が止まると生産が止まる |
| 概要と、移行・機能追加が必要になった背景(2025問2、2021問2) | Aを短く、B、C、D | 背景を具体的に。移行なら現行のデータの持ち方 |
| 業務目標と指標、収集元(2025問1) | Aを短く、D | 場面14の業務目標・指標・3つの収集元を中心に書く |
| 業務の内容と、人手でしかできなかった理由(2024問1) | Aを短く、D | 場面15の業務の内容と4つの理由を中心に書く |
| 利用者の特性と利用シーン(2019問1) | Aを短く、Bを短く、D | 場面7の利用者と利用シーンを中心に書く |

段落AとBをそのまま両方書くと550字を超える。設問アで概要以外も問われているときは、AとBをそれぞれ半分に削って、問われた項目に字数を回す。

## 数値を使わない表現集

採点講評は、数値が無いことを問題にしていない。問題にしているのは、理由や検討の経緯が無いこと、業務との関係が無いことである。ただし具体性は必要なので、数値の代わりに「誰が・どの場面で・何ができるようになったか」で書く。

### 言い換えの例

| 書きたくなる数値 | 代わりの書き方 |
| --- | --- |
| 応答時間は3秒以内 | 読み取った後、作業者が次の部品に手を伸ばすまでに結果が出る |
| バッチ処理は4時間以内 | 所要量計算の終了から倉庫の始業までに終わる |
| 在庫の精度が95%に向上 | 期末棚卸の差異が大きく減り、担当者が余裕を上乗せした発注をやめた |
| 出庫の工数を30%削減 | 応援者がベテランに尋ねずに出庫できるようになった |
| 追跡の時間を2日から10分に短縮 | 紙の記録をめくる作業が、画面での検索に変わった |
| 部品点数は3万点 | 部品点数が多く、構成の階層が深い |
| 利用者は300人 | 3工場の事務所、倉庫、製造ラインの利用者がいる |
| 可用性99.9% | 出庫が止まると生産が止まるので、現場系だけ水準を高くした |
| 読取りの精度98% | 印字された成績書はほぼ正しく読め、危険な読み違いには検査員が全て気付けた |

### 使ってよい数値

次の種類は、業務を知らない採点者でも妥当性を疑いようがないので、使ってよい。

- **会社と拠点の規模**：社員約1,000名、工場は3つ、営業拠点は国内5都市と海外2か国。
- **構造の数**：システムは4つの部分、比較した案は3つ、ペルソナは2つ。
- **回数と周期**：1日1回、平日と週末、月次、期末。
- **業務上の時点**：始業まで、当日中、翌日、期末の連休。
- **段階の数**：3段階で補った、2段階の構成にした。

### 気を付けること

- 「大幅に改善した」「効率が向上した」だけで終えない。必ず、人の行動がどう変わったかを添える。
- 効果を書くときは、設問アで書いた課題と同じ言葉を使う。課題が「部品を探すのに時間が掛かる」なら、評価も「探す」で書く。
- 規模を問われたら、社員数と拠点の数で答える。件数や金額は書かない。

## 残り6日の使い方

試験は11月20日である。新しい知識を増やすより、場面を「5行で言える」状態にすることに時間を使う。16の場面を全て同じ深さで覚える必要はない。まず★のある場面5・6・8・12・16の(2)と、どの問題にも使いやすい場面2・4・7を固め、残りは対応表で「どれを使うか」を言える程度でよい。

### 場面ごとに作る5行メモ

各場面を次の5行に縮めて、タイピングで書き出す。これがそのまま骨子になる。

1. 課題(業務の事情を含めて)
2. 比べた案(2つか3つ)と比較の軸
3. 選んだ案と理由、捨てた案の欠点
4. 結果と利用部門の評価
5. 残った課題と今後

### 本番での手順

1. 2問の設問ア・イ・ウを読み、対応表でどの場面が使えるかを決める。★のある場面を使える方を選ぶ。

5. どの段落にも「〜と考えた」「〜のため、〜とした」を入れ、理由を残す。
